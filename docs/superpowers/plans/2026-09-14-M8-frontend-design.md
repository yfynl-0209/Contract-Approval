## 0. 为什么在 M4 之前就写 M8 的文档

不是因为排期，而是因为**前端的需要会反向约束后端的数据结构与接口**。
下面三处如果拖到 M8 才发现，返工代价远大于现在：

| # | 缺口 | 拖到 M8 才发现的代价 |
| --- | --- | --- |
| **G-1** | **附件内容没有可用的获取接口**。工具 3 返回的 `file_path` 是给**外部系统 / MCP** 的（需求要求，不得删除），且依赖"服务器本地有文件"这一 M3 事实；对象键则属内部，不下发 | 详情页无法预览合同 → 只能临时加接口，且容易顺手去用 `file_path`，把前端绑死在本地文件实现上 |
| **G-2** | **证据里没有页面尺寸与坐标系**。证据结构是 `{page, bbox, char_start, char_end, precision}`，前端画高亮框必须同时知道 PDF 页的**原始宽高、坐标系（原点与单位）与旋转角** | "PDF 证据定位跳转"是模块 3 的验收项 → **M4 不补，M8 直接无法验收**；坐标系不声明则框会**上下翻转而不报错** |
| **G-3** | **"确认是否仍然有效"没有后端判据**。`review_results` 有 `content_digest` 与 `confirmed_digest` 两个字段 | 前端自己去比两个摘要 = **在浏览器里算业务口径**，直接违反 §9 的硬约束 |

> 因此本文档最有价值的部分是 **§6 接口与数据契约**：它规定了 M4/M7 必须产出什么。
> 页面设计本身（§4）反而是容易调整的那部分。

| --- | --- |

## 1. 事实核对

### 1.1 原始要求（不得改写）

> **五个模块必须完整**：待办调用 / 详情查看 / 解析结果 / 规则命中 / 结果处理。
> 规则管理与运行管理是**扩展入口**，**不得挤占五个原始模块的验收范围**。

## 3. 信息架构

```text
/                          总览（重定向到待办）
├── /tasks                 模块 1：待办调用
│   └── /tasks/:taskId     任务工作台（模块 2–5 的容器）
│       ├── ?tab=detail      模块 2：详情查看
│       ├── ?tab=parse       模块 3：解析结果
│       ├── ?tab=rules       模块 4：规则命中
│       └── ?tab=result      模块 5：结果处理
├── /rules                 扩展：规则管理
└── /ops                   扩展：运行管理
```

**为什么把模块 2–5 收在一个任务工作台里**：它们是**同一份合同的四种视角**，
审查人需要在"看到一条命中 → 跳证据 → 确认结果"之间来回切。
做成四个独立顶级页面会强迫用户反复进入退出，且丢失上下文。

`?tab=` 而非嵌套路由：切换视角**不应产生新的历史记录**，否则"后退"会退到上一个 tab，
与用户对"返回列表"的预期冲突。

## 4. 页面设计

### 4.1 模块 1：待办调用（`/tasks`）

**目标**：一屏看清"哪些要我处理"，尤其是**为什么卡住**。

```text
┌────────────────────────────────────────────────────────────┐
│ 待办调用            [状态▾] [回写▾] [阻塞▾] [搜索____]     │
├────────────────────────────────────────────────────────────┤
│ 汇总（来自后端 /api/tasks/summary）：                       │
│   待办 12 · 审查中 3 · 需人工 2 · 已完成 45 · 回写失败 1    │
├────────────────────────────────────────────────────────────┤
│ 编号            标题          申请人  附件 状态   总风险 回写│
│ HT-2026-0002   原材料采购…    李四    1    审查中  —      — │
│ HT-2026-0005   运维服务…      王五    2    ⚠阻塞   —       — │
│      └ 附件已被删除 · 阻塞于「下载」· ATTACHMENT_MISSING     │
│ HT-2026-0001   办公设备采购…  张三    1    已完成  高    成功│
└────────────────────────────────────────────────────────────┘
```

**关键设计点**

1. **阻塞原因内联展示**，不是藏在 tooltip 里：`blocked_stage` + `last_error_code` +
   `block_reason` 三件套同屏。只看"阻塞"两个字，用户必须点进去才知道该找谁。
2. **总风险来自最新批次**（`review_results.overall_risk_level`），未审查时显示 `—`
   **而不是"低"**。把"没审过"显示成"低风险"是最危险的一种默认值。
3. **回写列展示状态与原因两段**：`写失败` + `原因码`。见 §5.1。
4. 汇总卡片由 `/api/tasks/summary` 提供（§6.2），**不在前端 count**。

**空/错/加载态**

| 状态 | 呈现 |
| --- | --- |
| 加载 | 骨架屏（保留表头，避免布局跳动） |
| 空列表 | "暂无待办。可点「拉取待办」从审批系统同步。" + 按钮 |
| 拉取失败（5xx） | 红色横幅 + `error_code` + "稍后自动重试"（**不要显示成业务失败**） |

### 4.2 模块 2：详情查看（`?tab=detail`）

**目标**：确认"这份合同是什么、我们的立场对不对、有哪些附件"。

区块顺序（**按审查人的决策顺序，不按数据库表顺序**）：

1. **权威审查上下文**（最高优先级）
   - 展示四个业务事实：我方、合同标签、业务角色、合同类型；
   - `context_status` 三态呈现：

   | `context_status` | 呈现 | 可用操作 |
   | --- | --- | --- |
   | `complete` | 绿色标记"来自审批系统" | 可"人工修正" |
   | `missing` | **黄色警告**"立场未知，方向敏感的规则无法可靠判断" | 必须"人工确认" |
   | `conflict` | **橙色警告**"审批单声明与实际不一致，需人工裁定" | 必须"人工确认"+ 显示冲突双方 |
   | `confirmed` | 蓝色标记"已人工确认 by …" | 可再次修正 |

   > ⚠️ `missing` 必须显式警告。M3 已确定"刚拉取完的任务 `context_status` 就是 `missing`"，
   > 那是**正确行为**；若前端把它静默显示成普通字段，用户会以为系统已经知道立场了。

2. **审批表单**（`form_data_json`）
   - 原样展示键值对；**敏感值（证件号、联系方式）默认掩码**，点击"显示"才展开；
   - 页面不得把表单内容写进 URL、前端日志或错误上报。

3. **附件列表**
   - 每行：文件名、大小、类型、`download_status`、SHA-256 前 12 位、"预览"；
   - `download_status='failed'` 显示原因（`error_message`），并提供"重新下载"；
   - `available=false`（外部标记不可用）与 `failed`（我们下载失败）**区分呈现**——
     前者是外部事实，后者是我们的尝试结果。

### 4.3 模块 3：解析结果（`?tab=parse`）

**目标**：**验证**AI 的读取是否可信，并一键跳到原文位置。

布局：**左侧字段列表 + 右侧 PDF 预览**（可拖拽分栏）。

```text
┌──────────────────────┬─────────────────────────────────────┐
│ 解析版本 [v2 ▾]      │  contract_02_prepay.pdf   [1/6 页]  │
│ 覆盖率 0.94 · OCR 2页│ ┌─────────────────────────────────┐ │
├──────────────────────┤ │                                 │ │
│ 字段          状态   │ │      （PDF 渲染）                │ │
│ 合同总金额  ✓已提取  │ │      ┏━━━━━━━━━━━━━┓            │ │
│   ¥1,200,000         │ │      ┃ 高亮证据框  ┃            │ │
│   [定位 →]           │ │      ┗━━━━━━━━━━━━━┛            │ │
│ 预付款比例  ⚠不确定  │ │                                 │ │
│   [定位 →]           │ └─────────────────────────────────┘ │
│ 争议解决    ∅未发现  │                                     │
│ 签署日期    ✗解析失败│                                     │
└──────────────────────┴─────────────────────────────────────┘
```

**关键设计点**

1. **字段状态四态必须分别呈现**（`extracted` / `not_found` / `uncertain` / `failed`）：

   | 状态 | 呈现 | 用户该做什么 |
   | --- | --- | --- |
   | `extracted` | 绿色 ✓ + 值 | 可点定位核对 |
   | `not_found` | 灰色 ∅"文档可检索但未发现" | 判断是否真的缺失 |
   | `uncertain` | **黄色 ⚠**"证据不足，需人工判断" | 必须人工看原文 |
   | `failed` | **红色 ✗**"解析失败" | 联系管理员，不是"合同没有" |

   > ⚠️ `not_found` 与 `failed` **绝不可合并成"无数据"**。
   > 前者是"查过、没有"，后者是"没查成"—— 归因完全不同，
   > 合并会让用户把系统故障当成合同缺失（§10.2 明确禁止）。

2. **定位跳转**：点"定位"→ 右侧滚到对应页、画高亮框、必要时缩放；
   反向也成立：在 PDF 上框选 → 高亮"命中的字段"。

3. **解析版本可切换**：不同 `parse_version` 的证据**不得混用**（§10.4"绝不覆盖历史证据"）。
   切版本时 PDF 与字段列表**同时**切换。

4. **证据来源与可信度必须可见**：`ocr_confidence` 偏低时，字段旁标注
   "来自 OCR（置信度 0.72）"，并说明**该数值来自哪一页**。
   审查人需要知道"这条结论是猜的还是读的"。

   > 这里刻意**不用"降级"一词**：它描述的是"如实告知证据质量"，
   > 与 §10 ② 里被否掉的那种"能力缺失的降级"是两回事。
   > 同一个词指两个东西，迟早会被用来把要求换掉。

### 4.4 模块 4：规则命中（`?tab=rules`）

**目标**：回答"我要关注什么"，并且**默认不展示噪音**。

```text
┌────────────────────────────────────────────────────────────┐
│ 批次 v3 (2026-09-14 10:22)   命中 3 · 待判断 2 · 不适用 31 │
├────────────────────────────────────────────────────────────┤
│ ▼ 需人工判断 (2)                                           │
│  ⚠ 我方为采购方却约定 60% 预付款          [高]  [查看原文]│
│     原因: 立场上下文缺失 (CONTEXT_MISSING)                  │
│  ⚠ 乙方知识产权归属未明确                  [中]  [查看原文]│
├────────────────────────────────────────────────────────────┤
│ ▼ 命中 (3)                                                 │
│  ● 预付款比例超过 30%                     [高]  [查看原文]│
│     证据: "合同签订后 60 日内支付预付款"  第 2 页           │
│     计算: 60% > 30%                                        │
├────────────────────────────────────────────────────────────┤
│ ▶ 未命中 (4)  ▶ 不适用 (31)          ← 默认折叠            │
└────────────────────────────────────────────────────────────┘
```

**关键设计点**

1. **排序固定为 `needs_review` → `hit` → `not_hit` → `not_applicable`**，
   组内按 `risk_level` 降序。**`needs_review` 排在最前**：
   它不是"没结论"，而是"结论需要你来做"，属于**待处理**项，比已命中的风险更需要动作。
2. **折叠态必须能看到计数**（`▶ 不适用 (31)`）。折叠不等于隐藏，
   用户要能一眼确认"系统确实评估了 40 条规则"，这是**完整性**的可见性。
3. **`expr` 规则展示计算过程**（`hit_detail_json` 的 `actual` / `op` / `threshold`），
   而不是只给结论。审查人需要能复核"60% > 30%"这个判断本身。
4. **多处证据**：`evidence_json` 有多处时全部列出，点击任一处跳 PDF。
5. **原因码可见**（`reason_code` + `reason_text`）：`needs_review` 的原因决定
   用户下一步动作 —— "上下文缺失"要去补立场，"证据不足"要去看原文。

### 4.5 模块 5：结果处理（`?tab=result`）

**目标**：**确认后回写**，且明确知道"我确认的是哪一版正文"。

```text
┌────────────────────────────────────────────────────────────┐
│ 总风险：高        完整性：需人工判断（2 条待判断）          │
├────────────────────────────────────────────────────────────┤
│ 摘要                                                        │
│  本合同为我方作为采购方的设备采购合同，存在 3 处风险…        │
├────────────────────────────────────────────────────────────┤
│ 关注点                                                      │
│  1. 预付款比例 60%，高于内部标准 30%                        │
│  2. 未约定知识产权归属                                       │
├────────────────────────────────────────────────────────────┤
│ 回写正文（可编辑，编辑后需重新确认）                        │
│ ┌────────────────────────────────────────────────────────┐ │
│ │ 【风险审查意见】…                                       │ │
│ └────────────────────────────────────────────────────────┘ │
│ 正文摘要：a3f1c8…（与确认摘要 相同 ✓）                      │
├────────────────────────────────────────────────────────────┤
│ [ 确认并回写 ]     回写状态：未回写 · 原因：等待人工确认     │
└────────────────────────────────────────────────────────────┘
```

**关键设计点**

1. **"确认"针对的是具体一版正文**：界面必须显示
   `confirmed_digest == content_digest ✓` 或 `⚠ 正文已变更，确认已失效`。
   这个判断**由后端给出**（G-3），前端只渲染。

2. **编辑正文后确认立即失效**——前端在编辑框首次变更时就清掉"已确认"标记，
   但**最终判定以后端为准**（用户可能开着两个标签页）。

3. **回写状态与原因分两段展示**（§5.1）。

4. **门禁不通过不是错误**：`write_status='not_written'` + `reason_code='WRITEBACK_POLICY_DENIED'`
   应显示成"**暂不可回写**：高风险尚未人工确认"的中性提示，
   而不是红色错误。它是**正常的业务约束**，不是故障。

5. **不允许前端提前禁用"回写"以外的按钮**：`run_contract_rules` 等长任务按钮
   在任务处于 `blocked` 时应可再次触发（后端会拒绝非法转换并返回 409），
   前端不做状态机的第二份实现。

### 4.6 扩展：规则管理（`/rules`）

- 列表：`rule_code` / 名称 / 风险等级 / 匹配模式 / 适用条件 / 状态 / 版本；
- 操作：**启停用**、编辑**适用条件**（结构化表单，不做任意表达式编辑）、**版本发布**（`/api/rules/reload`）；
- 编辑后必须提示"影响面"：该规则的适用条件会让多少条待办改变结论（**由后端算**，若无此接口则不做）。

### 4.7 扩展：运行管理（`/ops`）

- **作业视图**：`workflow_jobs` 列表 —— `job_type` / `job_status` / `attempt_no` / `max_attempts` /
  `next_retry_at` / `last_error_code`；
- **日志视图**：`task_logs`，按 `log_level` 过滤，`error_code` 可点筛选；
  **支持按 `correlation_id` 检索**，并提供「复制追踪 ID」——
  让用户报障时能直接给出一个可检索的标识，而不是描述"大概是上午那次拉取"。
  （`correlation_id` 由 M4 引入，见计划 §12：它贯穿"请求 → 作业 → Worker"，
  因此这条检索是**异步执行段唯一的串联手段**）
- **重试入口**：从 `blocked_stage` 恢复（`POST /api/tasks/{id}/retry`），操作需填原因 → 写审计；
- **审计视图**：不可变事件列表（规则修改、上下文确认、结果确认、人工重试、评论回写）。

> 运行管理是**排障入口**，不是第二套业务界面：它**只读 + 重试**，
> 不允许在这里改任务状态。

## 5. 贯穿性约定（比单个页面更重要）

### 5.1 状态与原因必须**分两处**呈现

M3 已把这两者拆成两个正交维度：

```text
write_status = not_written    reason_code = WRITEBACK_POLICY_DENIED   ← 门禁拒绝
write_status = failed         reason_code = APPROVAL_API_ERROR        ← 外部系统故障
```

**前端不得只显示状态**。只显示 `not_written`（未回写）会让人以为"还没轮到"，
而实际可能是**门禁明确拒绝**——两者对用户意味着完全不同的动作。

> 这条正是 M3 那次收敛在前端的延续：**状态回答"走到哪一步"，
> 原因回答"为什么没成功"，合并呈现就等于把那次修正又抹掉了。**

### 5.2 业务结论 ≠ 系统故障

M3 定下的 REST 语义必须在界面上同样成立：

| 后端 | 语义 | 界面呈现 |
| --- | --- | --- |
| `200` + `outcome="blocked"` | **业务结论**（合同/附件本身有问题） | 🟡 待人工处理 + 具体原因 + 可用操作 |
| `5xx` | **系统故障**（审批系统不可用等） | 🔴 红色 + `error_code` + "稍后自动重试" |

把两者都渲染成"失败"是最常见的界面级退化：用户会对同一句话
（"附件下载失败"）采取错误动作 —— 前者该去找上传人，后者该等系统恢复。

### 5.3 所有操作按钮的禁用只是**提示**

前端的禁用/隐藏是 UX 优化，**权限与状态是否允许一律由后端判定**。
因此：**后端返回 4xx/409 时，界面必须能正确解释并刷新状态**，
而不是把它当成"未知错误"。这是"前端无法绕过门禁"的**可验证形式**。

### 5.4 数据获取与缓存（TanStack Query）

| 数据类型 | 策略 |
| --- | --- |
| 任务列表 / 汇总 | `staleTime: 10s`，切换筛选时按 key 重新请求 |
| 任务详情 / 解析 / 评价 / 结果 | `staleTime: 30s`，**不接受前端本地合并** |
| 长任务（解析、审查） | 轮询 `/api/tasks/{id}`，间隔 2s，成功后停止 |
| 变更操作（确认、重试、回写） | 成功后**失效相关 query**，不做乐观更新 |

> **不做乐观更新**：这些操作的成败由后端门禁决定，
> 前端先假装成功、失败再回滚，会让用户看到"确认了 → 又没确认"的闪烁，
> 而**中间那一瞬他已经以为生效了**。

### 5.5 错误呈现的三段式

任何失败都必须同时给出：**是什么**（`error_code`）、**为什么**（后端 `message`）、
**我现在能做什么**（后端返回的可用操作或建议）。

不允许只弹一句"操作失败"：那等于让用户去猜。

### 6.3 三处缺口的具体要求

**G-1：附件内容的可用形式**

**边界要说清**（两件事都成立，不矛盾）：

| | 说明 |
| --- | --- |
| 工具 3 **保留** `file_path` | 这是**原始需求的明确要求**（需求 2.4.4、企业化设计 §14："只有附件下载工具按需求返回受控的服务器临时工作路径"）。它是给**外部系统 / MCP 调用方**用的，**不得删除** |
| 工具 3 **不返回** `object_key` | 已于 2026-09-14 从响应移除。它是内部存储布局（`sha256/ab/cd/…`），下发会让调用方**依赖具体存储实现**，使 M9 换 MinIO 从"实现替换"变成"破坏性变更"。它仍完整保存在 `approval_attachments.object_key` |
| **前端不得用这两者取附件内容** | 前端走下面的 `/api/` 内容接口。`file_path` 依赖"服务器本地有文件"这一 M3 的实现事实，**M9 换成 MinIO 后根本不存在** |

> 也就是说：这两个字段都**不是内容获取手段** —— `file_path` 是给外部调用方的返回值，
> `object_key` 是纯内部标识。前端若依赖它们，等于把界面绑死在 M3 的本地文件实现上。

因此 M7 **必须新增**一个内容下发接口：

```text
GET /api/attachments/{attachment_id}/content
  → 200 application/pdf，支持 Range: bytes=0-…
  → Content-Disposition 用附件真实文件名（RFC 5987 编码）
  → 鉴权：RBAC + 任务可见性校验（不能靠 URL 猜）
  → 不返回服务器真实路径
```

M9 换成 MinIO 后，此接口可以改为"302 短期签名地址"或继续代理，
**对前端透明**——前端只依赖"这个 URL 能取到内容"。这正是把
`ObjectStorage` 抽象出来的收益之一。

**G-2：证据必须能定位到页面坐标（页面尺寸 + 坐标系 + 旋转角，三者缺一不可）**

前端画高亮框需要三个信息，而现有
`evidence_position = {page, bbox, char_start, char_end, precision}` **一个都没有**：

| 必须知道 | 缺了会怎样 |
| --- | --- |
| **页面尺寸**（width / height） | 无法把 bbox 从 PDF 坐标换算到渲染像素 —— 缩放后框整体偏移 |
| **坐标系**（原点位置 + 单位） | PDF 习惯原点在**左下**、屏幕在**左上**。不约定就必然出现**上下翻转**的高亮框，而且**看起来"有框"**，不会报任何错 |
| **旋转角** | 扫描件常见 90°/270°；不校正会让框整体错位到页面外 |

要求 M4 的标准文档模型输出（并写入 `parse_artifacts`）：

```json
{
  "page": 3,
  "width": 595.0,
  "height": 842.0,
  "bbox_space": "pdf-point-bottom-left",
  "rotation": 0,
  "source": "text"
}
```

> **为什么 `bbox_space` 必须显式写出，而不是靠"大家都知道 PDF 是左下原点"**：
> 这条约定要跨三个环节才能对齐 —— PDF 解析库 → 解析器 → 前端渲染库，
> 而 **pdf.js 用的是左上原点**。任何一环按自己的习惯理解，
> 结果都是"有框、但位置反了"：**不报错，只是看起来不对**，
> 而排查方向通常会被带向"坐标算错了"，忽略真正的分歧在**坐标系定义**。
> 显式写出来，才能让不一致在联调时立刻暴露。

**G-3：确认有效性必须由后端判定**

`review_results` 同时存 `content_digest`（当前正文摘要）与
`confirmed_digest`（确认时的摘要）。**两者是否相等属于业务判断**，
按 §9 硬约束**不能由前端比较**。要求 M7 在结果接口中直接返回：

```json
{ "manual_confirmed": true, "confirmation_valid": false,
  "confirmation_invalid_reason": "CONTENT_CHANGED" }
```

**G-4：`write_status` 有两个，口径必须先定义**

`approval_tasks.write_status` 与 `comment_logs.write_status` **同时存在**：

| 字段 | 自然含义 |
| --- | --- |
| `approval_tasks.write_status` | **任务级**：这条任务当前的回写进展 |
| `comment_logs.write_status` + `reason_code` | **尝试级**：某一次回写尝试的结果与原因 |

列表页要显示"回写失败"，结果页要显示"失败原因"——**两者可能来自不同的表**。
若不先定义口径，前端很容易在一个页面取任务级、另一个页面取最近一次尝试级，
于是同一个任务在两个页面上显示**不同的回写状态**。

要求 M7 明确并在接口文档中写明：

- 任务列表与汇总一律取 **`approval_tasks.write_status`**（任务级）；
- 失败原因取**最近一次** `comment_logs` 的 `reason_code` / `reason_text`，
  并在返回体中带上该次尝试的 `attempt_no` 与时间，**避免"原因属于哪一次"含糊**。

> 初稿写成"**(a) + 降级 (b)**"，把**要求**与**兜底**并列在同一格。这不是措辞问题，
> 后果很具体：**它等于预先授权了降级** —— M4 一紧张，就会有人指着
> "反正前端能降级"把页面尺寸与坐标系砍掉，而模块 3 的验收项
> "PDF 证据定位跳转"就此**永久退化**，且退化过程**没有任何一处报错**。
>
> **兜底的作用域是"单页数据缺失"，不是"能力缺失"**：
>
> | | 触发条件 | 谁来兜 |
> | --- | --- | --- |
> | 页面尺寸/坐标系/旋转角**缺失** | M4 没做 | **不兜**。这是 M4 的验收缺口，必须补 |
> | 某一页 OCR 失败、该页确实没有坐标 | 单页数据质量 | 前端那一页降级为文本级，并**如实标注精度** |
>
> 两者混淆的代价是**要求消失**——所以这一栏里必须只写 (a)。

## 11. 与 §4.1 的关系（本文件不等于 M8 的实施计划）

计划 §4.1 要求"每个里程碑单独生成实施计划"。本文件**不替代**那一步：

- 本文件是**前置输入**：它定的是接口契约与页面语义，这些在 M4 就要开始满足；
- 进入 M8 时仍需出「M8 设计确认 + 实施计划」，届时需要**重新确认**：
  组件库选型、真实合同上的渲染效果、M9 的签名形式、性能与分页细节、
  以及本文档 §10 六项决策的最终结论。

**现在写它的理由只有一个**：让 M4 与 M7 知道"前端要什么"，
而不是等前端开工时回头改数据结构与接口。
