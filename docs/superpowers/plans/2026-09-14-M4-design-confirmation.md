**本稿发现的两处第二稿内部矛盾**（评审未点破，但正是"必须改"的证据）：

1. §4.3 的**正文**写"换算需要 DPI/缩放矩阵与 **CropBox 偏移**"，而**公式**只有 `scale_x/scale_y`
   —— 文字与公式对同一件事给了两个答案；
2. §7 承诺"**所有** PyMuPDF 用法集中在 `app/adapters/parse/`"，而 §6 的 T2 写
   "**mock 因此引入 PyMuPDF 依赖**" —— 两句话不可能同时为真。

> 这两处的共同点：**每一边单独看都合理，合起来必错。**
> 而它们都藏在一份被反复复审过的文档里 —— 说明"读一遍文档"发现不了这类问题，
> **只有把两处并排放到一起、或者对着代码验一遍才能发现。**

**一处评审未在文档中举证的主张**：评审提到"`parse_version = MAX(...) + 1` 也有并发竞争"。
实测该写法**未出现在本文档任何位置**（全文检索 0 匹配），属**预防性建议**而非现有缺陷。
其担忧成立，因此约定：`parse_version` 的分配**必须**通过唯一约束冲突重试实现，
**不得**写成"先 `SELECT MAX` 再 `+1`"（§3.2 的唯一索引已使其失败可见而非静默）。

**验收标准由 20 条增至 31 条**：新增项集中于并发（缓存、租约、退避）、

**修-28 的根因值得单独说**：修-22 在 §3.2 写了
"`input_json` 携带已预留的 `parse_id`（**§4.5**）"，
但**只改了 §3.2**。那句括号引用看上去像"已经说完了"，
实际上是一个**指向空处的待办**。

> 差别只在于 —— 那次是**两份都写了的内容对不上**，
> 这次是**引用指向了一处不存在的内容**。
> 共同点是：**凡是"同一条规定出现在两处"，改完一处就必须立刻改另一处；
> 跨节引用要当成待办，不能当成已完成。**

**修-29 是三轮评审里第二个"需求缺口"**（第一个是修-23：工具 4 拿不到结果）。
它的形态值得注意：**页级状态定义得很细，却没有任何一处把它接到任务结论上**。
于是"文档为空"与"图片无法识别"这两条明确写进需求的 `blocked` 条件，
**在计划里根本没有落地的地方** —— 而所有页级验收都会通过。

> **修正与新增本身就是最高风险的变更**：看起来只是"补一个字段"，
> 实际却在改动多处**已经自洽**的约定，而那些约定此前的自洽正是靠"没有第九个字段"维持的。

而冲突的暴露方式是运行时的 `IntegrityError`，不是任何静态检查。

> 这是"分节撰写规范"的固有代价：**任何一条规定在被写下时，

> 应对办法只有一个 —— **把强约束（`UNIQUE` / `NOT NULL` / `CHECK`）摘出来集中核对一遍**，
> 因为它们的效果是"全库生效"，而写法却散落在各节。

#### 两条实测确认（PyMuPDF 1.25.1）

```text
页面 200x100、rotation = 90
  rawdict 字符 'A' 的原始 bbox = (10.0, 7.1)          ← 未旋转空间
  Point(10, 7.1) * page.rotation_matrix = (92.9, 10.0) ← 可见空间
  get_pixmap(Matrix(2,2)) = 200x400 = page.rect × 2    ← 旋转已在渲染中
```

**结论：两条路径的映射方向不同，且只有一条需要旋转。**

| 来源 | 原始空间 | 到显示空间 |
| --- | --- | --- |
| 文本层 `rawdict` | **未旋转** | 需 `page.rotation_matrix` |
| 渲染像素（OCR） | 像素，左上原点 | **仅缩放** |

只处理一条，会让"同一段文字、两种来源"的坐标**分处两个坐标系** ——
而两者单独看都合法，表现是证据框整体偏移、且偏移方向随页面旋转而变。

#### 新增的一个区分：`detected_lines` / `raw_confidence`

只看 `lines` 无法区分两种**结论相反**的情形：

| 情形 | `lines` | `detected_lines` | 结论 |
| --- | --- | --- | --- |
| 引擎什么都没找到 | 空 | `0` | `blank`（确实没内容） |
| 找到了但全低于阈值 | 空 | `> 0` | **`uncertain`**（有内容但读不准） |

合并成一个空列表，会让第二种被判成空白页 —— 而它的正确处置是
`blocked(OCR_UNRECOGNIZABLE)`（需求 §404）。这条通路**不会让任何断言失败**。

#### 一处自我纠错：源码级断言不能用文本判定

验收 40 要"源码级断言 `get_pixmap` 不含 `clip=`"。初版按**文本**判
（`"clip" not in 函数源码`），结果被 `_render_pixmap` **自己的 docstring** 绊倒 ——
那段说明里正写着"不得出现 `clip`"。**文本级检查分不清"提到"与"用了"。**
已改为 AST：查**调用关键字**与**属性访问**。

> 这与第六轮的模式一致：**断言写错时它会失败，但失败的原因不是缺陷** ——
> 那同样会浪费排查时间，甚至更糟（让人开始忽略这条断言）。
> 因此新增 `tests/test_parse_adapters.py` 时也一并断言了"反面"：
> 文本路径**必须**出现 `rotation_matrix`，否则"少做一次映射"这个方向的错误无人看守。

#### 两处根因同源：**把两件事塞进一个桶**

修-53（字段）与修-54（条款）表面是两件事，根因是同一个：
**一个清单同时承担了两种语义**。

| 桶 | 被合并的两件事 | 后果 |
| --- | --- | --- |
| `DIRECT_FIELDS` | 合同基本信息 / 规则计算字段 | 验收要的 8 项里有 4 项**根本不在桶里** |
| `CLAUSE_TYPES` | 需求规定的条款 / 已有规则消费的条款 | 为凑够 8 而合并两个语义不同的类别 |

两次都是数量对了（8 / 8），语义错了。而数量对了这件事**会让人以为已经对齐**。

#### 修-55 的教训：**复制的那一份一定会先偏离**

同一个"区间 → bbox"的判断在**两个模块各写了一遍**，于是两处同错。
这不是巧合：两份实现只有在**同时**被改对时才一致，
而它们分处两个文件、由两个不同的人在不同时间维护。

因此修法不是"把两处都改对"，而是**只留一处**：
`resolve_span()` 成为唯一入口，`locate()` 与字段提取器都调它。
后加的字段提取器不再有自己的一套几何判断。

#### `resolve_span()` 的对齐判据与降级

| 情形 | bbox | 精度 |
| --- | --- | --- |
| 块是 `char` 且区间正好是若干完整字符 | 命中字符 bbox 的**并集** | `char` |
| 块是 `char` 但 `chars` 覆盖不全（对不齐） | 整块 bbox | **降级为 `block`** |
| 块本来就是 `line` / `block` | 整块 bbox | 原样 |

降级分支在解析正常 PDF 上**走不到**（`DocumentBuilder` 产出的块总是逐字符覆盖的），
但仍用构造出的页面测了它 —— **走不到的分支里最危险的一种，
就是"以为它会降级，其实它标了 char"。**

#### 四态的分界做成**文档级前置条件**

`not_found` 只在"可靠检索过、确实没有"时成立，因此提取前先算一件事：
**这份文档有没有"我们没能读到的部分"？**

| 文档状态 | 未命中的字段 |
| --- | --- |
| 全部 `ok` / `blank` | `not_found` |
| 存在 `uncertain` 页 | **`uncertain`**（`EVIDENCE_UNCERTAIN`） |
| 存在 `failed` 页 | **`failed`**（`EXTRACTION_FAILED`） |

**单个 `blank` 页不算失败**（合同有空白背页很正常）：把它算成"没读到"，
会让每一份带空白页的合同都无法给出 `not_found` —— 缺失类规则全部退化成
`needs_review`，人工队列被无意义的复核塞满。

有失败页**只影响"未命中"的结论**：已读到的字段照常 `extracted`。
把整份文档判死会让"能读到的部分也没了"，那是另一个方向的浪费。

#### 修-51：`min_coverage` 默认 0.3 会把**每一份干净的文本 PDF** 判成"需要 OCR"

**这是本轮最有价值的一处发现，而且只有测试能抓到它。**

写 T7 测试时，六条内容测试同时失败在"页被路由到 OCR"。起初看像是假数据太稀疏，
于是去测量**真实夹具**的覆盖率：

| 夹具 | 字符数 | 文本面积 | 覆盖率 |
| --- | --- | --- | --- |
| `contract_01_clean.pdf` | 336 | 58 061 | **0.1159** |
| `contract_02_prepay.pdf` | 323 | 55 814 | **0.1114** |
| `contract_03_dev_no_ip.pdf` | 375 | 64 800 | **0.1293** |
| `contract_04_standard_goods.pdf` | 287 | 49 594 | **0.0990** |
| `contract_06_conflict.pdf` | 256 | 44 237 | **0.0883** |

真实 A4 上 30 行正文，文字面积只占页面的 **0.09 ~ 0.13**。
而初版阈值是 **0.3** —— 于是：

- 每一份文本 PDF 都去跑 OCR（慢）；
- 精度从 `char` **掉到** `line`，验收 1/6 的文本件断言直接不成立；
- 没有 OCR 引擎时，干净的文本件直接 `FAILED(OCR_MODEL_UNAVAILABLE)`。

**根因是一个语义错误**：`min_coverage` 被当成"文字应该占页面的多少"来设，
而它的用途其实是"抓**几乎没有文字**的页面"（水印/页眉页脚约 0.001）。
主力判据是 `min_chars`，它只是补充。已改为 **0.02**（低于真实值两个数量级）。

> **测试分层也是这轮暴露的**：六条内容测试与路由测试混在一起时，
> "假数据没通过阈值"伪装成"构建逻辑错了"，真正的问题藏在里面。
> 现在内容类用 `_LOOSE` 阈值，路由类与**真实夹具**用默认阈值 ——
> 后者才是"阈值本身对不对"的守卫。

#### `deadline.py` 的能力边界（必须写清，否则会被当成"真正的超时"）

超时后我们做的只是**不再等待**：PyMuPDF 与 ONNX Runtime 都是同步 C 调用，
**无法从外部中断**，那个调用仍在后台线程里跑。因此：

- 它解决"**Worker 永远阻塞**"，**不**解决"那个调用还在吃 CPU"；
- 反复超时意味着后台线程在累积，是"输入有问题或超时值太小"的信号
  —— 因此 `DeadlineExceeded` 带上标签（`render-page-3`）与超时值，必须能从日志里看出来；
- 真正能取消的方案要用**子进程隔离**（可杀），那是另一个量级的改动，M4 不做。

**关键取舍四：把"静默回落"做成可观测的。**

`_read_attachment_bytes` 仍保留兜底的运行时生成路径（M2 遗留）。
但夹具缺失时静默回落到 ASCII 占位 PDF，症状是"解析器什么都抽不出来"，
与病因相距很远。因此响应头加上 `X-Fixture-Source`（`fixture` / `contracts` / `generated`），
并由一条测试断言"**演示实例的附件全部来自夹具**"。

**一处对既有验收的连带修改**：M3 验收 8 的取证方式失效了。

这是 T11 的**配对夹具测试**抓出来的 —— 不是我预料会发现的东西。

| 项 | 内容 |
| --- | --- |
| **现象** | 同一份合同：文本件读出 `800000.00`，扫描件读出 **`800`** |
| **根因** | OCR 把 `800,000.00` 读成 `800，000．0０`（U+FF0C 全角逗号 / U+FF0E 全角句点 / U+FF10 全角零），而正则只认 ASCII 的 `[\d,]` —— **匹配到 `800` 就停了** |
| **性质** | **实质缺陷**。金额差 1000 倍，随后被拿去和阈值比较，**结论直接反转**；而日志、证据、界面**全都"看起来正常"**（`800` 也是一个合法的正数金额） |
| **修正** | `_fold_numeric()` 做 **NFKC** 折叠，用于 `_parse_amount` 与 `_to_number`；`value_text` 仍保留**原文**（页面上真实印着的东西，人要拿它核对） |

⚠️ **NFKC 只能作用在捕获到的值上，不能作用在页文本上**：它会**改变字符串长度**
（`㍿` 展开成 4 个字符），施加到整篇文本会让所有 `char_start/char_end` 与 `bbox` 一起错位。
捕获值的偏移不参与任何坐标计算，因此在那一层折叠是安全的。

⚠️ 并且**补了 4 条快速守卫用例** —— 真正抓到它的那条走真实 OCR、**默认跳过**。
没有快速用例，这个修复就没有常规守卫，而它下次会**静默复发**，
并且**任何集成方都不会发现**（`800` 不会触发任何异常）。

#### 修-60：领取语句的**防御性加固**与其**效力边界**

`claim_next_job` 的外层 `WHERE` 原先**只按 id 匹配**。子查询选出的候选 id 是
**读取那一刻**的事实，两个并发方可能读到同一个 —— 后写的那次会把已经 `running`
的行再写一遍，于是**同一个作业被跑了两遍**（重复的 OCR 推理）。已改为**重复一遍可领取条件**。

⚠️ 但**反向验证（撤掉加固，看演练是否会失败）显示：演练照样通过**。
原因是 **SQLite 是单写者模型**，并发的写事务被串行化，
"两个执行体读到同一个候选 id"这个窗口在本机**造不出来**。

因此 `tests/test_failure_drills.py` 里的并发演练在本仓库中的定位是**回归网**，
**不是**对并发正确性的证明 —— 已在测试文件里逐字写明。
真正的验证要等 **M9 换 PostgreSQL**（MVCC 允许两个事务同时选中同一行）。

> **写不出"会失败的断言"时，如实标注它的效力，而不是给它起一个听起来更强的名字。**
> 一条永远绿的断言比没有断言更糟：它会让下一个人以为这件事已经被守住了。

#### 修-61：**图片其实绕过了规范化，而它看起来完全正常**

按计划写完 `_image_to_pdf` 之后，测试给出的虚拟页宽度是 **595.2pt** —— 与 A4 几乎一致，
"看起来完全对"。但同一份内容按 **150 dpi** 渲染出来，宽度仍是 595.2pt，**没有成比例缩小**。

追下去才发现：`fitz.open(stream=png_bytes, filetype="pdf")` **会成功** ——
PyMuPDF 按**内容**自动识别格式，`filetype` 参数并不真的约束它。于是：

| 环节 | 实际发生的事 |
| --- | --- |
| 图片进 `_open_pdf_or_image` | 被 `fitz.open` 直接打开成"文档"，**从未进入** `_image_to_pdf` |
| 页面尺寸 | 由**图片自带的 DPI 元数据**决定，`IMAGE_ASSUMED_DPI` 是**死代码** |
| 为什么没被发现 | 测试用的 PNG 恰好带 300 dpi 元数据 → 页面**恰好也是 A4** |

**危害是分层的**：带 300 dpi 元数据的图片一切正常，
而手机拍的照片通常**没有** DPI 元数据（按 72 算）→ 页面与像素等大 →
4000 像素宽的照片得到 4000 磅宽的页面 → 渲染时直接撞 `PDF_TOO_LARGE_PIXELS`。
**一类图片正常、另一类直接失败，而失败原因指向渲染而非入口。**

修法：按魔数显式分流（`%PDF-` → PDF 路径，否则 → 图片路径），
不再让 `fitz.open` 去猜。并补了一条**能失败的断言**：
同一份内容按 300 / 150 dpi 渲染出的图片，虚拟页宽度必须**成比例**
（这条在"由元数据决定"的实现下**会失败** —— 那时两者都会被还原成同一个值）。

```text
    抽取文本 = 'PLACEHOLDER CONTRACT (mock data for M2)\n
                This page is generated at runtime by mock_approval.sample_pdf.'
    文本块数 = 1

    抽取文本 = ''      文本块数 = 0        ← 空白页
```

| M4 验收标志 | 现状下能否验证 |
| --- | --- |
| 文本件返回 **char 级**证据位置 | ⚠️ 只能验证"字符区间"，几何精度无内容可依 |
| 扫描件返回 **line 级** | ❌ **不能**。扫描页是空白页，OCR 读不出任何内容——只能证明"代码走了 OCR 分支" |
| **字段与条款提取** | ❌ **不能**。占位文字里没有金额、日期、主体、条款 |

> 这不是"夹具不够漂亮"，而是**验收项无法成立**。
> 带着现状进 M4，最可能的结局是把标准悄悄降级成"管线跑通了"。

**事实 B：PyMuPDF 的坐标系是"左上原点"。**

```
页面 rect = Rect(0.0, 0.0, 595.0, 842.0)；首个文本块 y0=59.1（靠近页顶、数值小）
→ y 从顶部向下增大 = 左上原点，与屏幕和 pdf.js 一致
```

仍然**必须显式声明** `bbox_space`：PDF 原生规范是左下原点，链上任何一环改用它就会**翻转且不报错**。

### 3.1 新表 `parse_artifacts`（第 11 张表）

```sql
CREATE TABLE IF NOT EXISTS parse_artifacts (
    id               INTEGER PRIMARY KEY AUTOINCREMENT,
    parse_id         INTEGER NOT NULL REFERENCES contract_parses(id) ON DELETE CASCADE,
    kind             TEXT NOT NULL,   -- standard_document / ocr_pages

```

**为什么完整页面与坐标进对象存储**（决策③）：一份 50 页扫描件的文本块可达数千条，
全部塞进 SQLite 会把"按任务查解析结果"变成全表扫描。
数据库只留对象键与摘要，与 M3 附件一致。

### 3.2 `contract_parses` 增 5 列（修-5 / 修-9 / 修-30 / 修-31）

```sql
parser_name      TEXT,   -- 解析器标识，如 "pymupdf"
parser_version   TEXT,   -- 解析器版本，如 "1.25.1+pipe-v1"
config_digest    TEXT,   -- 参与解析的配置摘要（DPI、阈值、白名单、规范化版本…）
cache_key        TEXT,   -- 上述三者与 source_checksum 的合成键
parse_error_code TEXT,   -- 【修-30】稳定错误码；与 parse_error 分工见下

-- ⚠️ 必须是**部分唯一索引**（修-31），不能是全局唯一
CREATE UNIQUE INDEX IF NOT EXISTS uq_parse_cache_key
    ON contract_parses(attachment_id, cache_key)
    WHERE parse_status IN ('pending', 'parsing', 'succeeded');
```

#### `parse_error_code` 不能省（修-30）

§4.10 写了 `parse_status = 'failed' + DOCUMENT_EMPTY` 这类组合，
而 `contract_parses` **只有 `parse_error TEXT`**（实测 `db/schema.sql`）——
那是给人看的自由文本，**无法承载机器判据**。

`approval_tasks.last_error_code` 与 `workflow_jobs.last_error_code` 替代不了它：
它们描述的是**任务/作业**当前的状态，而**历史解析记录**为什么失败
（第 3 次解析因为 `PDF_ENCRYPTED` 失败、第 1 次是 `DOCUMENT_EMPTY`）
只有 `contract_parses` 自己能回答。缺了这一列，
"这个附件历次解析分别因为什么失败"就只能靠读中文文本去猜。

> 这与本仓库的既有纪律一致（`ErrorCode` 的 docstring 已写明
> "必须与可读文本分开"）。§4.10 引入了一批新的机器错误码，
> **却没有给它安排存放位置** —— 又是"规定了结论、没规定承载"。

#### 为什么唯一索引必须是**部分**的（修-31）

修-9 要求 `UNIQUE(attachment_id, cache_key)`，修-22 又要求
"`failed` / `blocked` 的记录**不构成缓存命中**"。**这两条不可能同时成立**：

```text
第 1 次解析：失败 → 留下 (attachment, K) + parse_status='failed'
第 2 次解析：应当真正重跑，需要插入 (attachment, K) + 'pending'
           → 撞上全局唯一索引 → IntegrityError: UNIQUE constraint failed
```

也就是说，修-9 的写法让修-22 成了**一句无法执行的承诺**，
而且失败方式是运行时的 `IntegrityError`，不是启动时的校验错误。

**加上 `WHERE parse_status IN (...)` 之后两条要求才自洽**：

| 状态 | 参与唯一约束 | 效果 |
| --- | --- | --- |
| `pending` / `parsing` / `succeeded` | ✅ | 并发下只有一个能占位 → **只跑一次 OCR**（修-22 的核心） |
| `failed` / `blocked` | ❌ | **不占位**，历史留痕，允许重新解析 |

> SQLite 3.8.0+ 与 PostgreSQL 都支持部分唯一索引，两边语义一致。
> **这条是全项目最容易漏的一处不一致**：两条规定分别在两节、
> 各自都写得通顺，**只有把 SQL 与那句"不算命中"放在一起读，才会发现它们互斥。**

**必须区分两个"版本"**：

| 字段 | 回答的问题 |
| --- | --- |
| `parse_version` | **同一附件的第几次解析**（时序、序号） |
| `parser_version` | **由哪个解析器版本产生**（可比性、缓存命中） |

> 混用会导致一个具体错误：解析器升级后旧记录仍显示"版本 2"，
> 于是缓存判定命中同一条，**升级后的解析器永远不会被真正执行**。

**为什么缓存用唯一约束而不是"先查后插"**（修-9）：

两个**并发**的相同解析请求会同时查到"无缓存"，然后各跑一遍 OCR ——
重复的模型推理是最贵的一种浪费，而且两条记录都写进去了，
哪条是真的、`parse_version` 该算到几，都变成事后猜测。

唯一约束让"检查存在"与"创建"合成一个**原子动作**：
插入成功即"我创建的"，捕获唯一冲突即"别人建了，去读他的"。
这与 `workflow_jobs.idempotency_key`（M3）用的是同一套手法 ——
**并发下的正确性只能由数据库保证，"先查后写"一定会穿透。**

**但唯一约束只保证"不会有两行"，不保证"只跑一次 OCR"**（修-22）：

若两个 Worker 都**先 OCR、最后才插入**记录，唯一约束只能让第二个插入失败 ——
OCR 已经跑了两遍。而 OCR 恰恰是整条链路里最贵的一步，
"省一次模型推理"正是缓存存在的全部理由。**因此必须规定占位的时机**：

| 步 | 动作 | 归属 |
| --- | --- | --- |
| 1 | 事务内**创建或获取** `contract_parses`，状态 `pending` | 工具 4 的请求事务 |
| 2 | **同一事务内**创建或复用唯一解析作业，`input_json` 携带已预留的 `parse_id`（§4.5） | 同上，一次提交 |
| 3 | **只有成功创建占位行的那个请求**才入队、才由 Worker 执行 OCR | API → Worker |
| 4 | 冲突方**按幂等键查出那条作业**并返回它的 `job_id`，不入队、不跑 OCR（键的构造见下） | API |
| 5 | OCR 完成后把占位行推进到 `succeeded`，并写字段与工件（同事务，§4.4.3） | Worker |

> 关键是第 1 步落在**事务内**、且**早于** OCR。占位行是"这次解析已被认领"的凭证；
> 把它挪到 OCR 之后，唯一约束就从"防重复执行"退化成"防重复记录"了。

**解析作业的幂等键（修-42）**：

```python
build_idempotency_key(JobType.PARSE, str(parse_id), "v1")
# → "parse:18:v1"
```

⚠️ **`version` 不能留空**。M3 的 `build_idempotency_key` 在 `version=None` 时
会退化成**一次性键**（追加随机后缀）—— 那是为"拿不到外部版本"准备的安全退化。
用在这里会让**每次调用生成一个新键**，冲突方**永远查不到同一条作业**，
于是第 4 步失效、同一份文件被并发解析多次 —— 而这正是修-9/修-22 要防的事。
写死 `"v1"` 是因为 `parse_id` 本身已经是唯一标识，键只需稳定。

**顺带解决两件之前没定义的事（修-42）**：

| 问题 | 规定 |
| --- | --- |
| 冲突方**怎么查到**那条作业？ | 按上面的幂等键查 `workflow_jobs.idempotency_key`。**不需要给 `workflow_jobs` 加 `parse_id` 列** —— 键本身就是索引（`UNIQUE(idempotency_key)` 已存在） |
| **缓存命中**（占位行已 `succeeded`）时怎么办？ | **复用原作业与原 `parse_id`**，直接返回；**不新建作业**。本次调用写一条 `task_logs` 留痕 |

**为什么不给"这次调用"再造一条已成功的作业**：那会产生一批
**从未执行过、却标着 `succeeded`** 的作业记录。它们与真正的执行记录混在一起，
让"这份结果跑了几次、什么时候跑的"无法回答 ——
而作业台账存在的全部意义，就是回答这个问题。
**调用痕迹记 `task_logs`，执行事实记 `workflow_jobs`，两者不要互相冒充。**

**还有一条必须写死**：已存在记录为 `failed` / `blocked` 时**不构成缓存命中**（修-22）。
把失败结果当缓存复用，会让**一次瞬时故障永久固化为结论** ——
重试永远命中那条失败记录，用户看到"这个文件解析不了"，
而真正原因（当时 OCR 超时）早已无人知晓。

这也说明了为什么缓存不能只看"有没有记录"：
**记录存在只证明"有人试过"，不证明"试成功了"。**

**`cache_key` 的构成必须包含会改变结果的一切**（修-9）：

| 参与项 | 不参与会怎样 |
| --- | --- |
| 文件 `source_checksum` | 换了文件却命中旧缓存 |
| 解析器名 + 版本（PyMuPDF） | 引擎升级后仍复用旧结果 |
| 管线版本 | 路由/合并逻辑改了却不知道 |
| OCR 引擎与模型版本 | 换模型不生效 |
| DPI 与 OCR 阈值 | 调了参数看不出差别 |
| 字段提取规则版本 | 规则改了仍读旧字段 |
| 文本规范化版本 | NFC 规则变更后字符区间全部错位 |

> 前四条放进 `parser_version` / `config_digest` 两个字段即可，
> **不必新增列**：`cache_key` 是它们的摘要，两个字段保留原始值用于追溯。

**`parse_version` 的分配方式**（修-26）：

"唯一冲突重试"只说对了一半 —— 它保证不会写出重复版本号，
但**没有说明 `MAX(parse_version) + 1` 这个读操作在并发下的行为**。
必须先声明分配策略：

| 环境 | 方式 |
| --- | --- |
| SQLite（M4 现状） | 分配阶段用**短暂的 `BEGIN IMMEDIATE`** 把"读最大值 + 插入"串行化；冲突则重试 |
| PostgreSQL（M9） | 改为**序列**（sequence），或对附件行加锁后分配 |

**为什么不能只写"冲突重试"**：两个事务读到同一个 `MAX` 时，
失败的那个若要正确收敛，必须**重新读取**再试。
若直接重试而沿用陈旧值，它会一直撞同一个约束 ——
**表现为无限重试**，而日志里只有重复的约束冲突，看不出"忘了重读"。

### 3.3 `workflow_jobs` 增 6 列（修-2 / 修-3 / 修-10）

```sql
input_json        TEXT NOT NULL,   -- 不可变输入（结构见 §4.5）
input_digest      TEXT NOT NULL,   -- 输入摘要，用于幂等与追溯
correlation_id    TEXT,            -- 关联 ID（Worker 在另一进程，必须落库）
lease_owner       TEXT,            -- 持有租约的 Worker 标识
lease_token       TEXT,            -- 【修-10】每次领取都变化的 UUID
lease_expires_at  DATETIME,        -- 租约到期时间
CREATE INDEX IF NOT EXISTS idx_jobs_lease ON workflow_jobs(job_status, lease_expires_at);
```

**为什么 `input_json` 独立于 `checkpoint_json`**：后者是**可变**的执行进度，每次重试都可能被改写；
输入是**不可变**的。混在一起，"这份结果基于什么输入"永远无法回答。
也**不得**从 `idempotency_key` 反解析业务参数 —— 本仓库已有源码级守卫禁止该做法
（`tests/test_source_invariants.py`）。

#### `lease_token` 为什么不能省（修-10）

只用 `lease_owner + lease_expires_at` **不是 fencing**，它挡不住这种情形：

```text
worker-A 领取作业 42，lease_owner='w1'，租约过期
        ↓  A 卡住（GC / 换页 / 长时间 OCR）
回收 → 置回可执行；worker-B 领取同一作业 42，lease_owner 仍是 'w1'
        ↓  A 恢复，执行完成，提交 UPDATE
WHERE id=42 AND lease_owner='w1'  ← 匹配成功！
        →  A 用**过期租约**覆盖了 B 的结果，且没有任何报错
```

判据必须是**"这次领取"**而不是"哪个 Worker"：`lease_token` 在每次领取时重新生成 UUID，
旧执行提交时带的 token 已被覆盖，`WHERE` 自然匹配不到 —— 这才是 fencing。

> 这与 M3 作业幂等键的教训是同一个：**闸门必须绑定"这一次操作"，
> 而不是"这一类操作"**。绑定后者时，同一主体的第二次操作会顶掉第一次的合法性。

**还有一处必须写死在文档里**（修-10）：**租约回收后进入 `retry_wait` 并退避，不是直接 `queued`。**

直接置回可执行意味着"刚崩掉的作业立刻被下一个 Worker 捡起"。
如果崩溃的原因是这个附件本身（超大像素、损坏到触发引擎 bug），
就会形成**崩溃循环**：每次崩溃立即重试，几秒内烧光 `max_attempts`，
同时满载 CPU。退避给出的冷却期不是为了等待，而是为了**不让失败变成拒绝服务**。

### 3.5 升级方式（复审建议 / 修-11）

**SQLite 不会因为 `CREATE TABLE IF NOT EXISTS` 而给已有表加列** —— 既有 `data/app.db`
在加了 `parser_version` 之类的列之后**不会自动生效**，而报错会出现在查询时，不是启动时。

M4 开发阶段明确：

```powershell
# ⚠️ 备份文件名**必须带时间戳**（修-11）
Copy-Item data\app.db "data\app.db.$(Get-Date -Format 'yyyyMMdd-HHmmss').bak"
.\.venv\Scripts\python.exe scripts\init_db.py --reset
```

**为什么备份必须带时间戳**：固定名 `app.db.bak` 意味着**第二次执行会覆盖第一次的备份**。
而"再重置一次"恰恰常发生在"上一次重置之后发现问题、想回到更早状态"的时候 ——
那时需要的那份备份，正好已经被这次操作毁掉了。

**`--reset` 的适用边界必须写进脚本帮助文本**：它**只能用于开发库**
（`data/app.db`）。生产库不存在"重置"这个操作，
一旦有人把它指向真实数据，没有任何确认步骤能挡住 —— 因此要在入口处显式声明，
而不是靠使用者记得。（本阶段无生产环境，但约定先立。）

（Alembic 迁移归 M9；本阶段不做增量升级脚本，但**必须显式执行这一步**，
而不是假定"改了 schema 就已经生效"。）

## 4. 接口设计

### 4.1 端口：`app/ports/ocr_gateway.py`

```python
@dataclass(frozen=True)
class OcrLine:
    text: str
    bbox: tuple[float, float, float, float]
    confidence: float

@dataclass(frozen=True)
class OcrPageResult:
    page: int                       # **1-based**，与需求文档一致
    lines: tuple[OcrLine, ...]
    confidence: float
    # ---- 坐标契约（修-6）：必须随身携带，否则无法换算回 PDF 点 ----
    image_width: int                # 渲染后的像素宽
    image_height: int               # 渲染后的像素高
    bbox_space: str                 # "image-pixel-top-left"

@runtime_checkable
class OCRGateway(Protocol):
    def recognize(self, image: bytes, *, page: int) -> OcrPageResult: ...
```

### 4.2 标准文档 DTO（修-6 / 修-7 / 修-12）

**枚举必须拆成两个**（修-12）。既有的 `Precision`（`app/enums.py`）只有
`char / line / none` —— 它里面**根本没有 `block`**，因此 §4.2 与验收 6 里
出现的 `bbox_precision = block` **在类型上无法表达**，是文档与代码的直接冲突：

```python
class TextPrecision(StrEnum):
    """文本定位精度 —— 影响"证据文本是否可信"。"""
    CHAR = "char"    # 有字符区间
    LINE = "line"    # 只有行级文本（OCR）
    NONE = "none"

class BboxPrecision(StrEnum):
    """几何定位精度 —— 影响 M8 画框：char 画字符框，block 画块框并如实标注。"""
    CHAR = "char"    # 有逐字符 bbox
    LINE = "line"    # 只有行级 bbox
    BLOCK = "block"  # 只有块级 bbox
    NONE = "none"
```

**为什么不能共用一个枚举**：两个维度的取值域不同 ——
`block` 只对几何有意义（一段文本的"块级文本精度"不是一种精度），
`line` 只对文本有意义（块级 bbox 不存在"行级几何"这一档）。
共用一个枚举的代价是**每个使用点都要额外说明"哪些值在这里非法"**，
而漏说明的地方就会写出 §4.2 那样的矛盾。

```python
#: 归一化后的包围盒，约定 x0 <= x1、y0 <= y1
BBox = tuple[float, float, float, float]


class SourceSpan(BaseModel):
    """规范化后的一个字符，对应**原始文本**的半开区间 `[raw_start, raw_end)`。"""
    model_config = ConfigDict(frozen=True)
    raw_start: int = Field(ge=0)
    raw_end: int = Field(ge=0)


class DocumentChar(BaseModel):
    """一个字符 —— 存在它就说明几何精度真的是 char。"""
    model_config = ConfigDict(frozen=True, extra="forbid")
    text: str = Field(min_length=1)
    bbox: BBox
    char_start: int = Field(ge=0)     # 区间为 **[start, end)**
    char_end: int = Field(ge=0)


class DocumentBlock(BaseModel):
    model_config = ConfigDict(frozen=True, extra="forbid")
    block_id: str = Field(min_length=1)     # "p3-b12"
    text: str
    bbox: BBox
    char_start: int = Field(ge=0)
    char_end: int = Field(ge=0)
    text_precision: TextPrecision
    bbox_precision: BboxPrecision
    chars: tuple[DocumentChar, ...] = ()    # 【修-12】空元组 = 无逐字符几何


class DocumentPage(BaseModel):
    model_config = ConfigDict(frozen=True, extra="forbid")
    page: int = Field(ge=1)                          # 1-based
    width: float = Field(gt=0)                       # **旋转后可见页面**的宽（PDF 点）
    height: float = Field(gt=0)
    bbox_space: Literal["pdf-point-top-left"]
    rotation: Literal[0, 90, 180, 270]
    source: Literal["text", "ocr"]
    page_status: PageStatus
    route_reason: str | None = None                  # 走 OCR 的判据（阈值不满足项）
    error_code: str | None = None                    # 【修-38】仅 page_status='failed'
    char_map: tuple[SourceSpan, ...] = ()            # 【修-39】见下
    blocks: tuple[DocumentBlock, ...] = ()
```

#### 为什么改为 Pydantic 模型，而不是继续用 `@dataclass`（修-38）

第三稿把 `page_status` 从裸 `str` 改成 `PageStatus` 注解，**但这不产生任何校验**：
普通 `dataclass` 的注解只是类型提示，不在运行时检查。实测：

```python
D(page_status="illegal")     # 创建成功，实际类型仍是 str
```

于是**验收 44「非法状态写不进」在当前设计下根本无法成立** ——
它是一句靠注解"看起来实现了"的要求（与修-34 是同一类错误：
**以为改了声明就等于改了行为**）。

**规定**：

| 数据结构 | 用什么 | 理由 |
| --- | --- | --- |
| **标准文档 / `ParseJobInput` / `ParseOptions`**（需校验、需落库或序列化为 JSON 工件） | **Pydantic `BaseModel`**，`frozen=True`、`extra="forbid"` | 校验与序列化一体；读回工件时**同样**会校验 |
| **端口层的传递型 DTO**（`PendingApprovalDTO` 等，实测目前是 `dataclass`） | 维持 `@dataclass(frozen=True)` | 只在进程内传递、不落库，无需运行时校验 |

⚠️ **这个不对称是有意的**，不要为了"统一"把两侧都改掉：把端口 DTO 全改成
Pydantic 会给每次请求加一层无收益的构造开销；反之把标准文档改回 `dataclass`
则丢掉上面这条校验。

> 校验必须覆盖：**枚举取值、页码 ≥ 1、`rotation ∈ {0,90,180,270}`、
> bbox 已归一化、字符区间非负、`char_map` 与规范化文本等长**。
> 这些不是"锦上添花" —— 标准文档是**要落进对象存储并长期保存**的工件，
> 一份带着 `rotation=45` 或倒序 bbox 的工件，
> 会在 M8 画框时才暴露，而那时已经离产出它的代码很远了。

#### `char_map` 必须能表达"多对一"（修-39）

用 `tuple[int, ...]`（一个整数表示"规范化字符 → 原始下标"）**表达不了 NFC 的多对一**：

```text
原始： "e" + 组合重音      → 2 个码位
NFC ： "é"                → 1 个码位
```

一个整数只能指向**其中一个**原始字符，于是既无法表达
"两个原始字符共同组成一个规范化字符"，也无法据此算出**联合 bbox** ——
而那个字符的证据框恰恰需要覆盖两个原始字符。

**因此改为 `char_map: tuple[SourceSpan, ...]`**，每个规范化字符
对应一个原始半开区间（通常长度 1，多对一合并时长度 > 1）。

**验收 45 必须相应加强**：不能只断言"长度相等"，还要断言
**组合字符覆盖了正确的原始区间、且 `DocumentChar.bbox` 是原始字符框的并集** ——
只查长度的话，一个把 `SourceSpan(0,1)` 写成 `SourceSpan(1,1)` 的实现在长度上完全合法。

#### `error_code` 的取值域写错了（修-40）

第三稿注释为 `page_status='failed'/'blocked'` —— 但 **`PageStatus` 没有 `blocked`**
（四态是 `ok/blank/uncertain/failed`）。`blocked` 是**合同级与任务级**状态
（`contract_parses.parse_status` / `approval_tasks.task_status`），
不能出现在页级字段的取值域里。已改为仅 `failed`。

**`PageStatus` 必须是枚举**（修-34），取值四态：

```python
class PageStatus(StrEnum):
    OK = "ok"                # OCR / 文本层成功读出内容
    BLANK = "blank"          # 可靠识别后确认无文字
    UNCERTAIN = "uncertain"  # 有输出但置信度/覆盖不足
    FAILED = "failed"        # OCR 或渲染异常
```

第五稿把 `page_status` 写成裸 `str` 且注解只列了 `ok / blank / failed` ——
**正文随后又引入了第四态 `uncertain`**。裸 `str` 让这个遗漏不会被任何检查发现：
写错的值能一路存进工件，直到 M8 画框时才表现成"某页没有框"。

`route_reason` 同样必须**真的存在于 DTO**（修-34）：正文规定
"把判定结果写进 `page_status` 的依据中（`route_reason`）"，
而 DTO 里没有这个字段 —— 与修-28 的 `parse_id` 是同一种遗漏
（**正文规定了、承载结构里没有**）。

**为什么必须真的存 `chars`**（修-12）：初稿把 `bbox_precision` 标为 `char`，
但 `DocumentBlock` 只有一个**块级** bbox —— 那样一来
"我们有字符级几何"这句话没有任何数据支撑，M8 拿到 `char`
却只能画出块框，**验收 6 断言的正是这个能力**。

> 实测事实（§1.3）：PyMuPDF `rawdict` **确实**给出 91 个逐字符 bbox
> （首字符 `'采'` = `[60.0, 60.5, 72.0, 74.9]`）。所以问题不在"取不到"，
> 而在"取到了没存"。**能力声明与数据结构必须一起改，只改声明就是空头承诺。**

**`page_status` 的语义**（修-13 / **修-19 修正**）：

第三稿把"空白页 / 纯图片页"一并归为 `blank` —— **这是错的**。
一份扫描合同页在 OCR 之前**没有任何原生文本**，但它恰恰是**最需要 OCR** 的页面；
把它判成"空白"等于**在读取之前就宣布没内容**。正确的判定必须**按处理阶段**分开：

| 阶段 | 事实 | `page_status` |
| --- | --- | --- |
| 文本层无内容 | 尚未 OCR | **不是终态** → 进入 OCR 路由 |
| OCR 可靠执行后确认无文字 | 检索过，**确实没有** | `blank` |
| OCR 有输出但置信度低 / 覆盖不足 | **不确定有没有** | `uncertain` |
| OCR 或渲染抛错 | **不知道有没有** | `failed` + `error_code` |
| OCR 成功读出内容 | 确实有 | `ok` |

`uncertain` 这一档不可省：只有 `blank` / `failed` 两档时，
"读到了但读不准"只能二选一 —— 归 `blank` 会**丢掉内容**，
归 `failed` 会**谎报故障**，两者都让下游无法正确处置。

**"文本层够不够用"必须有明确阈值**（修-19）：判定"这一页要不要走 OCR"
不能靠"有没有拿到文本"这种布尔判断。必须给出可配置的判据并逐页记录，
否则两类页面会被**静默跳过 OCR**：

- 页面上只有**少量水印 / 页眉页脚**文字，正文是图片；
- 页面文本层是**乱码**（错误编码嵌入的字体）。

因此规定三个配置项 —— `min_chars`（最少字符数）、`min_coverage`（文本覆盖面积比）、
`max_garbage_ratio`（乱码字符比例上限）—— **任一不满足即走 OCR**，
并把判定结果写进 `page_status` 的依据中（`route_reason`）。
验收必须包含"**页面上只有少量水印文字、正文为图片**"这一用例（验收 25）。

不区分这些状态，下游只能把"失败页"当成"空页"处理：
字段提取走到这一页会得到"没找到" → 判 `not_found` → 触发"条款缺失"告警 ——
而真相是**我们没能读到那一页**。这正是 §4.8 强调的
`not_found` 与 `failed` 之分在**页级**的投影，缺了它，
"绝不把 OCR 失败谎报为 `not_found`"（验收 7）在页这一层就会被打破。

**同时规定的三件事**（否则"位置正确"无法验证）：

1. **字符区间为半开 `[start, end)`**，按页拼接、页间以一个 `\n` 连接；
2. **文本做 NFC 规范化**后再计算区间（否则同一字符的不同码位会让区间漂移）；
   ⚠️ **但规范化会改变字符数量**，因此必须同时保存
   **原始字符 ↔ 规范化字符的映射**（修-20）：NFC 会把组合序列合并
   （例如 `e` + 组合重音 → `é`，两个码位变一个），
   而 `chars[]` 里的 bbox 来自**原始**文本。没有映射时，
   第 N 个规范化字符找不到对应的原始 bbox —— 表现是
   **字符框整体向后错位，且越到后面偏得越多**，而文本与区间各自都是正确的；
3. `width/height` 对应**旋转后可见页面**，且 `rotation` 同时记录 ——
   两者缺一，M8 无法判断该不该做旋转补偿。

### 4.3 OCR 坐标换算（修-6 / 修-14）

初稿的换算是**等比缩放**：

```text
scale_x = page_width_pt  / W
scale_y = page_height_pt / H
pdf_bbox = (x0*scale_x, y0*scale_y, x1*scale_x, y1*scale_y)
```

**这个公式在四种常见页面下都是错的**，而它错的方式是"看起来对"（修-14）：

| 情形 | 等比缩放的结果 |
| --- | --- |
| **CropBox 原点非零** | 整页偏移，全部坐标等比错位 |
| **页面有 90°/270° 旋转** | 宽高互换，`scale_x` 用错基准 |
| **渲染时指定了裁剪区域** | 像素坐标系原点不是页面原点 |
| **旋转与裁剪同时存在** | 上面几种误差叠加 |

**正确做法：保存渲染矩阵，用它的逆矩阵回映射。**

⚠️ **但第三稿冻结的那段伪代码本身是错的**（修-21）。本机实测
（PyMuPDF 1.25.1，页面 `200x100`、`rotation = 90`）：

| 调用 | 实测结果 | 说明 |
| --- | --- | --- |
| `page.rect` / `page.mediabox` | `100x200` / `200x100` | 可见（旋转后） / 未旋转 |
| `get_pixmap(matrix=Matrix(2,2))` | **200x400** | = `rect` × 2 → **已含旋转** |
| `get_pixmap(matrix=rotation_matrix * Matrix(2,2))` | **400x200** | 退回了**未旋转**尺寸 |
| `get_pixmap(dpi=144)` | 200x400 | 与第二行一致 |
| `Matrix * Point` | **抛 `ValueError: Matrix: bad seq len`** | 乘法顺序写反 |
| `Point(20,40) * ~Matrix(2,2)` | `Point(10.0, 20.0)`，落在 `rect` 内 | 正确顺序 |

两条结论：

1. **`get_pixmap` 已经处理页面旋转**，再乘一次 `page.rotation_matrix`
   等于把旋转**撤销**：渲染出的是横图，而后续所有坐标推导都建立在它之上。
   第三稿那行伪代码正是这么写的 —— 它错在"以为旋转要自己补"；
2. **乘法顺序是 `Point * Matrix`**，写反直接抛异常（这条反而容易发现）。

修正后的写法：

```python
# ① 渲染：只给缩放，**不给 clip**（理由见下）
render = fitz.Matrix(scale, scale)
pixmap = page.get_pixmap(matrix=render)      # 尺寸 = page.rect * scale

# ② 回映射：Point * Matrix（不是 Matrix * Point）
to_pdf = ~render
p0 = fitz.Point(x0, y0) * to_pdf
p1 = fitz.Point(x1, y1) * to_pdf
bbox = (min(p0.x, p1.x), min(p0.y, p1.y), max(p0.x, p1.x), max(p0.y, p1.y))

# M4 不做区域裁切：始终整页渲染 + 整页 OCR（理由见下）
```

#### `clip` 参数必须避开（修-32）

第三稿的公式假设 pixmap 的像素原点 = 页面原点。**用 `clip` 渲染时这不成立** ——
此时像素 `(0,0)` 对应的是**裁剪区的左上角**，而 `~render` 仍算出页面原点。
实测（`scale = 1`、`clip = Rect(40, 20, 140, 80)`）：

| rotation | clip 传入 | 裁剪后 pixmap | `Point(0,0) * ~render` | 真实页坐标 |
| --- | --- | --- | --- | --- |
| 0 | `100x60` | **100x60** | `(0, 0)` ❌ | `(40, 20)` |
| 90 | `100x60` | **60x60** | `(0, 0)` ❌ | 见下 |
| 270 | `100x60` | **60x60** | `(0, 0)` ❌ | 见下 |

出错是必然的，而且**偏移会整页平移**（不是随机误差），于是所有证据框都错位。

**但"加一个偏移量"也修不好**：rotation = 90 / 270 时，
裁剪结果从 `100x60` 变成 `60x60` —— 说明 **`clip` 的坐标系随旋转改变**
（被与旋转后的显示矩形求交了），并不是"在未旋转空间里取一块"。
这种情况下裁剪区与像素的对应关系不再是单纯平移，
**继续用 `clip` 就得把整套几何重推一遍** —— 而那正是本轮反复出错的地方。

**因此 M4 的规定是：渲染一律不传 `clip`；需要限定区域时在像素空间裁切。**
代价是大页面会多占内存，而这一点**已由"超大渲染像素"上限兜住**（§7 五类边界之一）。

> 这条的教训比它本身更重要：**避免一个参数，比正确使用它更可靠。**
> 本轮三次坐标缺陷（重复旋转、缺文本层映射、clip 偏移）都来自
> "以为某个参数只是简单叠加"。**凡是不确定语义的参数，先问它能否不用。**

**另一件第三稿完全没提的事：文本层路径也要做同样的映射**（修-21）。

实测：`page.get_text("rawdict")` 给出的是**未旋转**空间坐标 ——
在未旋转坐标 `(10, 20)` 写入文字后，`rawdict` 返回
`(10.0, 8.17, 33.23, 23.29)`；若它已是旋转后空间，x 应落在 70–90 附近。

而 §4.2 声明标准文档使用**旋转后可见空间**。因此
**文本层与 OCR 层都必须经过一次转换才能对齐到同一空间**。
只处理 OCR 一条路径，会让"同一段文字、两种来源"的坐标
**分处两个坐标系**，而两者单独看都合法 —— 于是证据框整体偏移，
且偏移方向随页面旋转而变。

**因此不要把具体公式冻结在计划里**（本条的由来）：
设计一个 `RenderTransform` 值对象，**同时**持有
`render`（实际用于渲染的矩阵）、`to_pdf`（其逆）与 `source`（text / ocr），
并在页面级记录**实际生效的渲染区域**（CropBox 生效后的矩形）。
正确性由"**非零 CropBox 原点 + 90° 旋转**"的组合夹具验证（验收 5），
**而不是由文档里的公式保证** —— 公式只能说明意图，夹具才能证明结果。

**为什么必须存矩阵而不是"把 scale 和 rotation 拼起来算"**：
错在把各因素当成**可分离**的 —— 它们是同一次仿射变换的组成部分，
顺序与组合方式由渲染器决定。自己拼一个近似公式，就是在
**重新实现一遍渲染器已经算过的东西**，且只在"旋转为 0 且无裁剪"时碰巧正确。

> 与 §4.2 的教训相同：**能力声明必须由数据结构承载**。
> 只记录 `scale + rotation` 两个数，表达式上就无法还原一般仿射变换。

#### M4 **不做**区域裁切（修-41）

第三稿写了一句"需要限定区域时在像素空间裁切"，配的伪代码是
`region = pixmap[top:bottom, left:right]`。**这句话错了两层**：

| 错处 | 实测 / 说明 |
| --- | --- |
| **根本跑不起来** | `TypeError: 'Pixmap' object is not subscriptable` —— `Pixmap` 不支持下标 |
| **而且坐标照样偏移** | 即使先转 NumPy/PIL 再裁，OCR 返回的是**裁剪区内**的局部像素坐标，必须加回 `full_x = local_x + left`、`full_y = local_y + top`，**然后**才能乘逆矩阵 |

第二点才是关键：**我为了避开 `clip` 的偏移，却引入了一个自己的偏移。**
"不用 `clip`"并没有自动消除这个问题 ——
**只要渲染的是页面的一块，像素原点就不再是页面原点**，
无论那一块是 `clip` 参数还是手工切出来的。

**因此 M4 的最终规定：不做区域裁切，始终整页渲染 + 整页 OCR。**

- 区域裁切**从来不是需求**，只是曾经设想的省内存手段；
- 大页面的内存风险**已由"超大渲染像素"上限兜住**（§7 五类边界之一）；
- 少一个变换环节，就少一处"两边都对、合起来错"的位置 ——
  本轮四次坐标缺陷里有三次来自多余的变换环节。

**将来若确有必要做区域裁切**，必须先定义
`PixelCropTransform(left, top, scale)`，把链条一次写清：
**局部像素 → 整页像素（加回 left/top）→ PDF 显示空间（乘逆矩阵）**，
并配一条"非整页 + 已旋转"的验收 ——
**不允许再出现"先切一刀、后面照旧"这种局部修改。**

**换算必须由解析管线做，而不是要求每个 OCR 实现都会**：
换算需要 DPI、渲染矩阵与 CropBox 偏移，属**解析侧**知识；
要求各厂商适配器各自换算，等于把同一份几何知识复制到每个实现里，且很难测。

> ⚠️ **只断言"bbox 落在页面范围内"证明不了位置正确**，它只证明没越界。
> 因此验收项 5 改为：**用已知位置的合成文本**（我们在固定坐标写入文字）
> 反查 OCR 结果是否落在该位置附近（容差内），且**必须包含
> "非零 CropBox 原点 + 90° 旋转"的组合用例** —— 单独测旋转、单独测偏移，
> 每一种都能靠"碰巧"通过，组合起来才不会。

**⚠️ 与 M8 的接口必须写死方向**（修-14）：

**标准文档里的 bbox 一律已换算到旋转后的显示空间。**
M8 直接用它画框，**不得再应用一次 `rotation`** —— 否则旋转页的画框会转两次，
在 90°/270° 页面上表现为框跑到页面外面。这是典型的"两个模块各自做对了一半"
产生的缺陷：单独看两边都合理，合起来必错，因此必须有一方**明文放弃**这个动作。

### 4.4 Worker 的领取与租约（修-1 / 修-2）

```python
def claim_next_job(session, *, job_types, worker_id, now=None, lease_seconds=...):
    """原子领取一个可执行的作业；没有则返回 None。

    步骤顺序即正确性：
    1. 先回收**租约已过期**的 running 作业（§4.4.2）；
    2. 再用**单条 UPDATE ... WHERE id = (SELECT ... LIMIT 1)** 领取；
    3. 领取时写 lease_owner / lease_expires_at，并由 `mark_running` 递增 attempt_no。
    """
```

#### 4.4.1 `attempt_no` 语义（修-1，**防止重复扣预算**）

现有 `mark_running()` 已在**开始执行时**递增 `attempt_no`（`app/workflow/jobs.py`）。因此：

| 动作 | 是否递增 | 理由 |
| --- | --- | --- |
| 领取（开始一次执行） | **递增一次**（由 `mark_running` 完成） | 它确实是一次新的执行尝试 |
| 租约回收 | **不递增** | 它不是新的执行，而是"上一次执行失联"这一事实被记录 |
| 进程内重试 | 递增（同一轮内继续累积） | 与 M3 既有语义一致 |

> **初稿的错误**：让"领取递增"与"回收也递增"同时存在 →
> **同一次崩溃消耗两次额度**，`max_attempts=3` 实际只允许约 1.5 次真实重试。
> 这类缺陷不会报错，只会让"重试次数"变成名义值。

回收时的判定：读**现有** `attempt_no` —
`< max_attempts` → 置为 **`retry_wait` + 指数退避**（**不是 `queued`**，理由见 §3.3）；
`>= max_attempts` → `failed`，并让任务 `blocked(stage='parse')`。

#### 4.4.2 租约所有权与条件完成（修-2 / 修-10）

**条件必须同时匹配 `lease_owner` 与 `lease_token`**（修-10）：

```sql
-- 完成作业：带租约条件，影响行数为 0 表示"我已失去所有权"
UPDATE workflow_jobs
   SET job_status = 'succeeded', finished_at = :now,
       lease_owner = NULL, lease_token = NULL, lease_expires_at = NULL
 WHERE id = :id
   AND lease_owner = :worker_id
   AND lease_token = :token          -- 【修-10】绑定"这一次领取"
   AND job_status  = 'running'
   AND lease_expires_at > :now;
```

`lease_token` 不可省的理由与失效场景见 §3.3 —— 一句话：
**只匹配 `owner` 时，重启或卡顿后恢复的旧执行仍会通过校验。**

**影响行数为 0 时必须作废本次结果并记日志**，而不是继续写业务数据。

#### 4.4.3 写业务结果与完成作业，必须在**同一事务**里（修-10）

顺序不是风格问题，写反了会出现"数据写了、状态没写"的半截状态：

```text
1. BEGIN
2. 用 lease_token 条件校验所有权（SELECT ... FOR UPDATE 语义 / 先做条件 UPDATE）
3. 写 contract_parses、parse_artifacts
4. 条件更新作业为 succeeded（带 lease_token）
5. COMMIT —— 一次提交
```

**为什么"先校验、后写"不够，必须同事务**：如果第 2 步在事务外、
或者完成作业失败后不回滚业务写入，就会出现这种结果：

```text
旧 Worker：写入 contract_parses（成功）
         → 条件更新作业，影响行数 0（已失去所有权）
         → 若此时才检查，业务数据**已经落库**，且不会被任何状态标记为可疑
```

于是库里多了一份**没有任何作业引用它**的解析结果，而新 Worker 稍后
又写入自己的一份。`(attachment_id, parse_version)` 的唯一约束会挡住重复，
但挡住的方式是**新 Worker 报错**——它对用户表现为"解析失败"，
而真正的问题在旧 Worker 的越权写入。**症状与病因完全错位。**

因此：**所有权校验是事务的第一步，业务写入与状态更新一起提交，要么都成，要么都不成。**

> 这与 M3 的 `transactional_session`（一个调用 = 一个事务）是同一条原则。
> 差别只在于：这里的事务由 **Worker** 而不是 HTTP 请求开启。

**对象存储不参与事务**（修-27）：`parse_artifacts` 的工件写在对象存储里，
而对象存储**没有事务** —— 数据库回滚**不会**把已写入的对象删掉。
因此顺序必须固定：

1. **事务外**先把工件以**内容寻址**方式幂等写入对象存储（同内容重复写是安全的）；
2. 进入数据库事务：重新验证租约 → 写 `contract_parses` / `parse_artifacts` 引用 → 条件完成作业；
3. 提交。

**为什么不能反过来（先提交、后写对象）**：那会产生**悬空引用** ——
库里有 `object_key`，去取却 404。孤儿对象只是浪费空间，
而悬空引用是**证据丢失且无法察觉**：报告已经生成，原始工件却取不回来。

代价是可能留下**孤儿对象**（写了对象但事务回滚）。因此需要清理机制：
定期比对对象存储中的键与 `parse_artifacts.object_key`，
删除**无引用且超过保留期**的对象。

**归属：M9**（修-36）。第五稿只写"这件事不在 M4 做"，
**没有指向任何里程碑** —— 那是"知道有、没人管"的标准形态：
写在文档里像已经处理了，读起来也不刺眼，但**永远不会有下一次被提起的机会**。

归 M9 的理由：M9 本来就要用 MinIO 替换本机存储、
并处理存量对象的迁移与生命周期策略，孤儿清理与那些工作**共用同一套扫描逻辑**，
现在做会在换存储时重写一遍。

> 凡是"明确不做"的事项，**必须同时写明归谁、在哪个里程碑验收**。
> 只写"不做"，等于把它从待办里删掉了。

**长任务续租**：解析一份 50 页扫描件可能远超租约时长，
因此每处理完一页/一个阶段就延长 `lease_expires_at`（同样带 `lease_token` 条件）。
**续租失败（行数为 0）= 已失去所有权 → 立即停止并放弃写入。**

### 4.5 作业输入契约（修-3 / 修-15）

**先解决一个真实歧义**（修-15）：初稿写 `{"attachment_id": "A-1002"}`，
但库里**同时存在两个都叫 attachment 的标识**：

| 字段 | 是什么 | 例 |
| --- | --- | --- |
| `approval_attachments.id` | 本系统**数据库主键**（INTEGER） | `37` |
| `approval_attachments.attachment_id` | **外部审批系统**的附件编号 | `"A-1002"` |

两者都能被称为"附件 id"，而 `"A-1002"` 恰好是**外部**那个。
若接口层与作业层各自理解成不同的一个，解析会拿到**另一份附件**，
或者报"附件不存在"—— 而两个组件各自的日志都是对的。

**统一规定**（工具 4 与作业输入共用）：

```text
document_id = approval_attachments.id       ← 本系统主键，全局唯一且稳定
```

**作业输入字段同时改名，让歧义不可能再出现**：

```json
// workflow_jobs.input_json
{
  "parse_id": 18,
  "attachment_record_id": 37,
  "source_checksum": "4320ee10…f7493d9",
  "object_key": "sha256/43/20/4320ee10….pdf",
  "content_type": "application/pdf",
  "parse_options": { "dpi": 200 }
}
```

**`parse_id` 必须在输入里**（修-28）：§3.2 规定占位行**先于**作业创建
（在同一事务里预留），Worker 的职责是**填充那一行**，而不是新建一行。
缺了它会出现两个具体后果：

| 后果 | 说明 |
| --- | --- |
| Worker 只能**猜**目标记录 | 通常退化成用 `(attachment_id, cache_key)` 反查 —— 而修-15 刚把"从哪里取标识"统一掉，这里又开了个后门 |
| `result_ref.parse_id` **没有稳定来源** | §4.6 承诺"作业成功时 `parse_id` 已确定"，但若它不在输入里，这个承诺就只是文档里的一句话 |

> **这正是"同一条规定写在两处、只改一处"的后果**：修-22 在 §3.2 写了
> "`input_json` 携带已预留的 `parse_id`（§4.5）"，而 §4.5 当时并没有改 ——
> 交叉引用指向了一处不存在的内容。**跨节引用必须当成待办事项去落实，而不是当成已经说完。**

- **不可变**：作业创建后不再修改；重试沿用同一输入；
- `input_digest` = 上述内容的 SHA-256，用于追溯"这份结果基于什么输入"。

**每种 `job_type` 定义严格的输入模型**（修-15），复用 M3 已有做法
（`app/schemas.py` 的 `ToolRequest`：`extra="forbid"` + `frozen=True`），
**不接受任意 JSON**：

| `job_type` | 输入模型 |
| --- | --- |
| `pull` | `{provider, tenant_id}` |
| `detail` | `{provider, tenant_id, instance_id}` |
| `download` | `{attachment_record_id, attachment_id, file_name?}` |
| `parse` | `{parse_id, attachment_record_id, source_checksum, object_key, content_type, parse_options}` |
| `parse`（模型名） | `ParseJobInput` —— 显式定义，**不接收裸 dict** |

**`parse_options` 也必须是模型，不能是一袋 JSON**（修-35）：

```python
class ParseOptions(BaseModel):
    model_config = ConfigDict(extra="forbid", frozen=True)

    dpi: int = Field(default=200, ge=72, le=600)
    ocr_min_confidence: float = Field(default=0.6, ge=0.0, le=1.0)
    min_chars: int = Field(default=20, ge=1)            # §4.2 的文本层判据
    min_coverage: float = Field(default=0.02, ge=0.0, le=1.0)  # 【修-51】原 0.3，见下
    max_garbage_ratio: float = Field(default=0.2, ge=0.0, le=1.0)
```

第五稿的 `{ "dpi": 200 }` **没有定义任何边界**，于是 `dpi=1` 或
`ocr_min_confidence=5.0` 都能进库，问题只在渲染/判定时才浮现 ——
而那时离"参数写错"这个真正的原因已经很远了。

**每个字段都必须有默认值与取值范围**（修-35）：
默认值让"不传"有意义，范围让"传错"当场被拒。
这与 M3 的 `ToolRequest`（`extra="forbid"` + `Field(ge=, le=)`）是同一套做法 ——
**没有范围的数值参数，等于把校验推迟到最难排查的时刻。**

**为什么必须严格**：作业输入由外部调用方（工具 4）或上游服务生成，
**键名拼错**是常见错误。宽松解析会让 `sourc_checksum` 这类笔误被静默丢弃，
作业照常入队、照常"成功"，只是用默认值跑了一遍 ——
调用方以为参数生效了。这与 M3 拒绝未知字段是同一条理由。

**关于幂等键的表述修正**（修-3）：

> 初稿写的"**不得**把业务参数塞进 `idempotency_key` **之外**的地方"
> 把意思说反了 —— 读起来像"只能放进 `idempotency_key`"，而 §3.3 明确
> "**不得**从 `idempotency_key` 反解析"。正确表述是：

**业务输入必须写入 `input_json`，不得只塞进 `idempotency_key`，也不得从键里反解。**

理由：`idempotency_key` 是**摘要**，为去重而设计，一旦有人依赖"从键里能读出参数"，
它就同时承担了"去重键"与"数据载体"两个角色 ——
之后任何改键格式的优化都会变成**破坏性变更**，而且破坏方式是
"读出来的参数变成了另一个值，不报错"。

### 4.6 `TaskRef` 与最小查询接口（修-4）

```json
{ "job_id": 42, "task_id": 7, "status": "queued", "status_url": "/api/jobs/42" }
```

**为什么必须有 `job_id`**：一个审批任务可以产生多个作业（多个附件、多次重试），
只用 `task_id` 无法回答"我刚提交的那次解析怎么样了"。

M4 增加最小接口（M7 再扩展为完整的任务/作业/日志查询）：

```text
GET /api/jobs/{job_id}
  → { job_id, task_id, job_type, job_status, attempt_no, max_attempts,
      next_retry_at, last_error_code, last_error_text, status_url,
      result_ref }        ← 【修-23】成功时非空

result_ref（job_status = 'succeeded' 时）:
  { "parse_id": 18, "result_url": "/api/parses/18" }

GET /api/parses/{parse_id}
  → { parse_id, task_id, attachment_id, parse_status, parser_version,
      parse_error_code, parse_error,            ← 【修-30】机器码 + 人读文本
      basic_info, clause_info, quality: { text_coverage, ocr_pages, ocr_confidence } }
```

**为什么必须有 `result_ref` 与 `/api/parses/{parse_id}`**（修-23）：

原始需求里工具 4 是 `parse_contract_document(document_id)` → **返回结构化字段**。
第三稿的接口只回了"作业跑得怎么样"，没有任何指向**结果**的东西 ——
于是调用方只能知道"完成了"，却**拿不到工具 4 该给的东西**。
这不是接口不够丰富，而是**需求没被满足**，且不满足的方式很隐蔽：
所有验收都通过（作业确实 `succeeded`），只有真的去用才会发现拿不到结果。

`result_ref` 放在作业响应里而不是新建一个异步查询接口，理由是
**作业状态与结果之间需要有一个可原子读取的关联**：
调用方拿到 `succeeded` 的那一刻，`parse_id` 必须已经确定
（§4.4.3 的同事务保证这一点），否则会出现"状态成功了但结果还不知道在哪"的窗口。

`basic_info` / `clause_info` 直接内联返回，**不要求调用方再去对象存储取工件**：
工具 4 的契约是"返回结构化字段"，让调用方自己拼装会把这个契约
推给每个集成方，而工件的布局（§3.4）是本系统的实现细节。

### 4.7 `correlation_id` 规范（决策④）

| 项 | 规定 |
| --- | --- |
| 来源 | 接受请求头 `X-Correlation-ID`；缺省由服务端生成 **UUID4** |
| 校验 | 调用方传入时须满足 `^[A-Za-z0-9._:-]{1,128}$`；**不合法 → 400** |
| 传递 | 请求入口存 `contextvar` → `LogService` 自动带上 → `create_job` 写入作业 → Worker 读回注入 |
| 清理 | 请求结束后**重置 contextvar**，避免线程池复用导致串号 |
| 索引 | `task_logs.correlation_id` 与 `workflow_jobs.correlation_id` **都建索引** |

**为什么不合法就报 400 而不是静默替换**：静默替换会让调用方手里的 ID
与我们库里的对不上 —— 他以为能查到，实际上永远查不到，且**没有任何提示**。

**为什么用 `contextvar` 而不是给每个函数加参数**：加参数意味着
**每一处新增的日志调用都可能忘记传**，而漏传的表现是"日志少了一段"——
不报错、不告警，只在排障时发现追不下去。

### 4.8 字段 JSON 契约（修-8 / 修-16）

`basic_info_json` / `clause_info_json` 内部的**统一结构**（M5 与 M8 消费）。

**根结构必须带 `schema_version`**（修-16）：这两个字段是**长期存放**的，
而契约会随 M5/M8 演化。没有版本号时，读到一个缺字段的旧记录，
消费方无法区分"旧格式"与"数据损坏"，只能加防御性判断 ——
那种判断一旦写错就变成静默的默认值。

```json
{
  "schema_version": 1,
  "fields": [
    {
      "field_code": "contract_amount",
      "value_text": "人民币 1,200,000.00 元",
      "value_decimal": "1200000.00",
      "currency": "CNY",
      "status": "extracted",
      "evidence": [
        { "page": 1, "block_id": "p1-b3", "text": "合同总金额：人民币 1,200,000.00 元",
          "bbox": [60.0, 120.5, 480.0, 138.9], "char_start": 88, "char_end": 118,
          "text_precision": "char", "bbox_precision": "char" }
      ],
      "reason_code": null,
      "reason_text": null
    }
  ]
}
```

**金额绝不用 JSON 浮点数**（修-16）：

| 写法 | 后果 |
| --- | --- |
| `"normalized_value": 1200000.00` | 浮点数在 JSON 往返与语言间可能存在精度损失；**金额上不可接受** |
| `"value_decimal": "1200000.00"` + `"currency": "CNY"` | 十进制**字符串**精确保留，币种独立成字段 |

不只用字符串，还因为**币种必须单独存**：把 `"人民币 1,200,000.00 元"`
整体当一个值，M5 的金额阈值规则只能对中文串做匹配 ——
既无法比较大小，也无法处理"USD 200,000"与"CNY 1,200,000"这类**不可比**的情况。
拆成"十进制数值 + 币种"两个字段后，比较币种是否一致成为**可判断**的事。

- `status` 取 `FieldStatus` 四态；
- **`reason_code` 必须是稳定枚举**（修-16）：`not_found` 时它**不**用来写检索范围，
  而取 `ReasonCode` 之类的稳定值（本仓库已有 `app/enums.py` 的 `ReasonCode`，
  其 docstring 已规定"中文解释放 `reason_text`"）。**检索范围、说明文字一律放 `reason_text`。**
  把自然语言塞进 `reason_code` 会让它无法统计、无法看板、无法断言 ——
  这三件事正是它存在的理由；
- `failed` / `uncertain` 时 **必须** 给 `reason_code`（否则 M5 无法判 `needs_review`）；
- **覆盖需求规定的 8 项基本信息 + 8 类条款**，不能只验收"金额 + 日期 + 一条知识产权缺失"。

### 4.9 任务状态推进与多附件聚合（修-8）

| 情形 | 任务状态 | 作业状态 |
| --- | --- | --- |
| 入队 | `pending → parsing` | `queued` |
| 解析成功 | `parsing → reviewing`（**且全部目标附件完成**） | `succeeded` |
| 确定性失败 | `blocked`，`blocked_stage='parse'` | `failed` |
| 瞬时失败 | **不变**（任务不阻塞） | `retry_wait` |
| 重试耗尽 | `blocked`，`blocked_stage='parse'` | `failed` |
| 缓存命中 | 与"解析成功"相同 | **复用原作业**（`succeeded`，**不新建**）；本次调用写 `task_logs` 留痕（§3.2 修-42） |

**多附件聚合规则（修-17）**：

初稿写"'非目标附件'（如已被外部删除的）**不计入**完成集合，但需在任务日志中说明" ——
**这条与 M3 已冻结的语义直接冲突**：

> M3 验收标准 9：附件缺失 → 附件 `failed`、任务 `blocked`、
> 错误码 `ATTACHMENT_MISSING`（19/19 验收已通过，见 M3 实施计划）。

**"只记日志、继续推进"是另一种规则**，两者不能同时成立。
采用 M3 的语义（缺失即阻塞），因为它的理由是**证据完整性**：
一份本该在册的合同正文拿不到，我们**没有资格**给出"本次审查完成"的结论 ——
而"不计入集合"会让任务安静地进入 `reviewing`，
产出一份**看起来完整、实际上漏了一份合同**的报告。

**正确的聚合规则**：

| 情形 | 任务状态 |
| --- | --- |
| 外部附件**不可用或缺失** | **`blocked`**（`blocked_stage='parse'`，`ATTACHMENT_MISSING`） |
| 类型受支持且**下载成功** | 进入解析集合 |
| 类型受支持但**尚未下载完成** | 保持 `parsing`（**不提前放行**） |
| **全部目标附件**解析成功 | 进入 `reviewing` |
| **没有任何可解析的合同附件** | **`blocked`**（例如全部为不支持的类型） |

后两行是一对：**"全做完"才放行，而"没有可做的"不是"做完了"**。
把空集合当成"全部完成"是这类聚合最典型的错误 ——
它让"任务只有不支持类型的附件"这种情形产出"审查通过"。

**支持的类型必须覆盖需求规定的图片扫描件**（修-17）：

```text
application/pdf
image/png
image/jpeg
```

**实测事实**：当前配置 `attachment_allowed_types = "application/pdf"`（`app/config.py`），
**只有 PDF** —— 与原始需求包含图片扫描件不符。

M4 因此有两条路，**必须明确选一条并如实记录**：

1. 扩白名单至上述三项（推荐）：扫描件本就要走 OCR 路由，
   而纯图片附件是"扫描件"最自然的形态；
2. 若本阶段只做"图片型 PDF"（即 PDF 内含扫描图，仍属 `application/pdf`），
   **必须在文档中显式记为"尚未完全满足需求"**，
   不能以"OCR 已跑通"为理由宣告 M4 完成 ——
   **跑通了引擎 ≠ 支持了需求里那一类输入**。

**但仅仅"允许这三种类型"不够：图片没有 PDF 坐标系**（修-24）。

标准文档（§4.2）把 `bbox_space` 固定为 `pdf-point-top-left`，
而 PNG/JPEG **没有 PDF 点、没有 CropBox、没有页面旋转角**。
直接让图片走同一条管线，会出现"声明写 `pdf-point-top-left`、
数值实为像素坐标"的情况 —— **声明与内容不一致**，
而下游（M8 画框、证据反查）会**照声明处理**，于是框画到错误位置，
且图片与 PDF 混在一个任务里时只有图片那部分错。

**M4 拍板：把图片规范化为"单页虚拟 PDF"**，再统一使用 PDF 点：

```text
image/png, image/jpeg
  → 包成单页 PDF（页面尺寸 = 图片像素按固定 DPI 折算成点）
  → 此后与普通 PDF 走**完全相同**的路径（渲染 / OCR / 坐标映射 / rotation = 0）
```

**为什么选这条，而不是"给标准文档再加一种 `image-pixel-top-left` space"**：

- 后者意味着 **M8 与所有证据消费方都要写两套坐标处理**，
  而两套之间的分叉只在"图片附件"这一类上暴露 —— 长期维护成本；
- 前者让 `bbox_space` 保持**单一取值**，代价只是解析入口处一次转换，
  且转换点固定，**下游无法感知附件原始格式**。

> 与 §3.4 同一原则：**唯一真相来源越少越好**。
> 每多一种坐标系，就多一处"两边都对、合起来错"的可能 —— §4.3 的重复旋转就是这么来的。

### 4.10 解析质量门禁：页状态 → 合同 → 任务（修-29）

§4.2 定义的是**页面级**状态，而需求说的是**文档级**与**任务级**的结论：

> 原始需求：**文档内容为空 → `blocked`**；**图片无法识别 → `blocked`**。

只有页状态、没有门禁，会出现一条**静默的错误通路**：

```text
扫描件页 OCR 返回一堆乱码（没有抛错）→ 页面 uncertain
  → 解析"成功"（确实读到了字）
  → 任务 reviewing
  → 基于乱码文本做规则评价，产出一份**看起来完整**的报告
```

**没有任何一条断言会失败** —— 每一页都处理过了。因此必须补上聚合判据：

| 情形 | `contract_parses.parse_status` | 任务 |
| --- | --- | --- |
| **全部页面**可靠识别后均为空 | `failed` + **`DOCUMENT_EMPTY`** | `blocked(stage='parse')` |
| **任一页面**最终 `failed` | `failed` | 解析失败；重试耗尽后 `blocked` |
| 扫描页出现 `uncertain`（**默认即视为无法识别**） | `blocked` + **`OCR_UNRECOGNIZABLE`** | `blocked`，进入明确的人工处理 |
| 全部页面 `ok`（允许个别 `blank`） | `succeeded` | 参与 §4.9 的聚合 |

**三处容易写错的地方**：

1. **单个 `blank` 页不是失败** —— 合同有空白背页很正常。
   构成失败的是"**全部**页面均为空"（那说明整份文档没有可读内容）。
   判据必须是**全称**，写成"存在 `blank` 即失败"会把正常合同判死；
2. **`uncertain` 默认判 `blocked` —— 第五稿的"容忍比例"是需求偏差，本稿撤回**（修-33）。

   原始需求写得很直接：**图片无法识别 → `blocked`**（需求 §404）。
   第五稿允许"少量 `uncertain` 页面继续进入 `reviewing`"，
   **这不是技术实现细节，而是把需求的结论改了** ——
   需求要的是"识别不了就停下来找人"，而容忍比例意味着
   "识别不了也可以继续出报告"。两者不是同一个产品行为。

   **本稿改为**：

   | 情形 | 结论 |
   | --- | --- |
   | 出现 `uncertain` 页 | **`blocked`** + `OCR_UNRECOGNIZABLE`（默认） |
   | 若将来确要放宽 | **必须作为"经确认的需求偏差"单独记录**（谁确认、放宽到什么值、为什么），不得由实现方默认采用 |

   即使将来放宽，也必须先定清四件事，否则"容忍比例"只是个说法：
   **参数名、默认值、计算公式（按页数还是按面积）、边界行为（恰好等于阈值时算不算超出）**。
   第五稿只写了一句"容忍比例可配置"，**没有一项**是可实现的。

   无论哪种取值，**证据不足的字段一律判 `uncertain`，不得当作 `not_found`** ——
   这一条与门禁的宽严无关，是字段层的独立要求；
3. **门禁是进入 `reviewing` 的前置条件** —— §4.9 说"全部目标附件解析成功才进 `reviewing`"，
   这里的"成功"必须指 `parse_status = 'succeeded'`（**已过质量门禁**），
   而不是"作业跑完了"。否则门禁形同虚设：作业 `succeeded` 但质量不合格，
   任务照样进入 `reviewing`。

#### M4 必须新增的错误码（修-29）

`ErrorCode` 现有取值里**没有**文档级与 OCR 类错误码
（实测：只有 `ATTACHMENT_*` / `STORAGE_*` / `OBJECT_NOT_FOUND` 等）。
M4 需在 `app/enums.py` 增加下列值，**并同步登记重试性**：

| 新码 | 类别 | 含义 |
| --- | --- | --- |
| `DOCUMENT_EMPTY` | 确定性 | 全部页面确认无文字 |
| `OCR_UNRECOGNIZABLE` | 确定性 | 扫描页无法可靠识别 |
| `OCR_MODEL_UNAVAILABLE` | 确定性 | 模型缺失 / 配置错误（§7） |
| `OCR_INFERENCE_TIMEOUT` | **瞬时** | 推理超时（§7） |
| `PDF_ENCRYPTED` | 确定性 | 加密文档（§7 五类之一） |
| `PDF_CORRUPT` | 确定性 | 损坏文档 |
| `PDF_TOO_MANY_PAGES` | 确定性 | 超过页数上限 |
| `PDF_TOO_LARGE_PIXELS` | 确定性 | 渲染像素超限（内存保护） |
| `PDF_RENDER_TIMEOUT` | **瞬时** | 渲染超时 |

⚠️ **两个"瞬时"码必须同时进入 `RETRYABLE_ERROR_CODES`**。
`is_retryable()` 对**未知码一律返回 `False`**，所以漏登记的表现是：
**一次推理超时就把任务打死**，而日志里的错误码看起来完全正常 ——
它只是被当成确定性错误处理了。

反向错误同样危险：把 `OCR_MODEL_UNAVAILABLE` 登记成可重试，
会让一个**配置错误**重试到预算耗尽，把真正的原因（模型路径写错）掩盖成"服务不稳定"。

## 5. 验收标准

| # | 验收项 | 验证方式 |
| --- | --- | --- |
| 1 | 文本件返回 **char 级**位置，且能反向匹配标准文档文本块 | `char_start/char_end` 切出的子串 == 证据文本 |
| 2 | 扫描件返回 **line 级**，且 **OCR 确实读出了内容**（非空） | `HT-2026-0005`：`text_precision == line`，文本非空 |
| 3 | **同一份内容**的文本件与扫描件，提取的关键字段**一致** | 配对夹具（决策①）：两种 kind 渲染同一份中文文本 |
| 4 | 标准文档含**页面尺寸 + 坐标系声明 + 旋转角** | 三者非空，`rotation ∈ {0,90,180,270}` |
| 5 | **坐标换算正确**：已知坐标写入的文本，OCR 结果落在**容差内**；**必须含"非零 CropBox 原点 + 90° 旋转"的组合用例** | 单独测旋转、单独测偏移都能靠碰巧通过，组合才不能；不满足于"落在页面范围内"（那只证明没越界） |
| 6 | **双精度如实标注**：`TextPrecision` 与 `BboxPrecision` 分别断言；`bbox_precision == char` 时 **`chars` 必须非空**，无逐字符 bbox 时只能为 `line` / `block` | 断言与**数据结构所承载的能力**一致 —— 只有声明没有 `chars` 就是空头承诺 |
| 7 | 四态语义正确：`not_found` 只在可靠检索后确实没有时出现 | 缺 IP 条款→`not_found`；OCR 失败→`failed`/`uncertain`，**绝不 `not_found`** |
| 8 | **字段 JSON 覆盖 8 项基本信息 + 8 类条款**，结构符合 §4.8 | 逐项断言 `field_code` 存在与结构合法 |
| 9 | **解析版本不覆盖历史**：不同 `parser_version` 产生两条记录并存 | 旧证据仍可读 |
| 10 | **缓存可追溯**：`cache_key` / `parser_name` / `parser_version` / `config_digest` 均已落库 | 同一文件 + 同版本重复解析**不重复 OCR**（假适配器计数为 0） |
| 10b | **缓存并发原子性**：两个相同解析请求**并发**发起时，不产生两条记录、只跑一次 OCR | **部分唯一索引**（`WHERE parse_status IN ('pending','parsing','succeeded')`）生效；捕获唯一冲突方复用既有记录（真并发，不是顺序调用两次） |
| 11 | **重试预算不被重复扣**：一次崩溃只消耗一次额度 | 租约回收后 `attempt_no` 不变 |
| 12 | **租约条件完成（fencing）**：失去所有权的 Worker **不得**写入结果 | 构造租约过期 + 旧 Worker 完成 → 影响行数 0，结果作废并记日志 |
| 12b | **`lease_token` 真的生效**：同一 `worker_id` 两次领取后，**旧 token** 提交必须失败 | 只换 `owner` 测不出问题（那正是初稿的漏洞）；必须固定 `worker_id`、让 token 变化，否则这条等于没测 |
| 12c | **写结果与完成作业同事务**：越权写入时业务数据**不得**落库 | 越权路径跑完后 `contract_parses` / `parse_artifacts` 无新增行 |
| 12d | **回收后走退避**：租约回收的作业进入 `retry_wait` 而非 `queued` | 回收后 `next_retry_at` 非空；避免崩溃循环瞬间烧光 `max_attempts` |
| 13 | **`TaskRef` 可查询**：工具 4 返回 `job_id`，`GET /api/jobs/{job_id}` 能查到状态 | 长任务不阻塞请求（< 1s 返回） |
| 14 | **多附件聚合**：任务须等**全部目标附件**完成才进 `reviewing` | 两附件夹具，只完成一个时任务仍为 `parsing` |
| 14b | **外部附件缺失 → `blocked`**（与 M3 验收 9 一致），**不得**"只记日志继续" | 构造一份缺失附件的任务 → `blocked` + `ATTACHMENT_MISSING`，且**不进入** `reviewing` |
| 14c | **无任何可解析附件 → `blocked`**：空集合不等于"全部完成" | 全部附件类型不受支持 → `blocked`，**不得**产出"审查通过" |
| 14d | **图片扫描件受支持**：`image/png` / `image/jpeg` 可走完 OCR 链路 | 白名单含三项；否则**显式记为未满足需求**，不得判定 M4 完成 |
| 15 | **`correlation_id` 贯穿**：一次请求的日志（含 Worker 段）共享同一 ID | 按 ID 查库同时命中 API 段与 Worker 段 |
| 16 | `correlation_id` **非法输入被拒**（400），不接受超长/非法字符 | 构造非法头 |
| 17 | **OCR 不可用时降级**：端口抛错 → 页面 `failed`，**不谎报 `not_found`** | 注入 OCR 故障 |
| 18 | 异常 PDF 五类边界：**加密 / 损坏 / 超页数 / 超大像素 / 渲染超时** | 分类正确（确定性 vs 瞬时） |
| 19 | 日志**不含合同正文** | 扫描 `task_logs.log_content` |
| 20 | **既有测试全绿**（M3 结束时 477 条，随里程碑增长；**以 `pytest` 实际输出为准**） | `pytest` |
| 21 | **空白页与失败页可区分**：`page_status` 取 `blank` / `failed`，失败页带 `error_code` | 构造空白页 → `blank`；注入 OCR 故障 → `failed`，且该页**不**产出 `not_found` |
| 22 | **作业输入拒绝未知字段**：每种 `job_type` 的输入模型 `extra="forbid"` | 构造含拼错键（如 `sourc_checksum`）的输入 → **被拒**，不得静默按默认值入队 |
| 23 | **金额无浮点**：字段 JSON 中金额为十进制**字符串**且币种为独立字段 | 遍历字段 JSON，断言无 `float` 型金额；币种字段非空 |
| 24 | **工件与字段不重复存储**（§3.4）：`contract_parses` 不存坐标，工件不存字段结论 | 库中无坐标列；工件 JSON 内无 `field_code` |
| 25 | **OCR 路由阈值生效**：页面只有少量水印/页眉文字、正文为图片时**必须走 OCR** | 构造该页 → 不得因"有原生文本"而跳过 OCR（§4.2 修-19） |
| 26 | **`uncertain` 页状态存在**：OCR 有输出但置信度或覆盖不足 → `uncertain`，**不得**归入 `blank` 或 `failed` | 注入低置信 OCR 输出 → `uncertain`，且该页**不**产出 `not_found` |
| 27 | **文本层与 OCR 坐标同空间**：旋转页上，文本层路径得到的 bbox 与 `page.rect`（旋转后可见空间）一致 | 90° 旋转页：文本证据 bbox 落在 `rect` 内，x/y 对应关系正确（§4.3 修-21） |
| 28 | **工具 4 能取到结果**：作业成功时 `result_ref.parse_id` 非空，`GET /api/parses/{parse_id}` 返回结构化字段 | 端到端调用工具 4 → 拿到 `basic_info` / `clause_info`（§4.6 修-23） |
| 29 | **图片附件坐标统一**：`image/png` / `image/jpeg` 经单页虚拟 PDF 规范化后 `bbox_space` 仍为 `pdf-point-top-left` | 遍历标准文档，断言 `bbox_space` 取值域**只有一个**（§4.9 修-24） |
| 30 | **失败记录不构成缓存命中**：`failed` / `blocked` 的既有记录**不阻止**重新解析 | 先制造一次失败解析 → 再次调用必须**真正重跑**，不得直接返回旧失败结果（§3.2 修-22） |
| 31 | **NFC 映射正确**：规范化前后字符数量不同时，`chars[]` 的 bbox 与字符区间仍指向同一字符 | 用含组合字符的文本构造 → 第 N 个字符的 bbox 与其区间对齐（§4.2 修-20） |
| 32 | **门禁：整份为空 → `blocked`** | 构造全空文档 → `parse_status='failed'`、`DOCUMENT_EMPTY`、任务 `blocked(stage='parse')`（§4.10 修-29） |
| 33 | **门禁：页面失败 → 解析失败** | 注入某页最终 `failed` → `parse_status='failed'`；重试耗尽后任务 `blocked`（§4.10） |
| 34 | **门禁：无法识别 → 不得 `reviewing`** | 大比例低质量页 → `blocked` + `OCR_UNRECOGNIZABLE`，**不进入** `reviewing`（§4.10） |
| 35 | **门禁是 `reviewing` 的前置条件**：附件 `parse_status != 'succeeded'` 时任务不得进入 `reviewing` | 一附件失败、其余成功 → 任务停在 `parsing` / `blocked`（§4.10） |
| 36 | **新错误码重试性正确** | 逐码遍历 `is_retryable()`：两个"瞬时"码为真、其余为假。**不抽查**（§4.10） |
| 37 | **`parse_id` 在作业输入中** | 缺 `parse_id` 的输入**被拒**；Worker 填充的行 == 预留的 `parse_id`（§4.5 修-28） |
| 38 | **单个 `blank` 页不判失败** | 两页夹具（一页空白 + 一页正常）→ `parse_status='succeeded'`，不得触发 `DOCUMENT_EMPTY`（§4.10） |
| 39 | **失败后可重新解析**：`failed`/`blocked` 记录**不占**唯一约束位 | 先失败一次 → 再次调用**不抛 `IntegrityError`**、新记录为 `pending`、OCR 真实重跑（§3.2 修-31） |
| 40 | **渲染不使用 `clip`，也不做区域裁切**（始终整页渲染 + 整页 OCR） | 源码级 AST 断言 `get_pixmap` 调用**不含 `clip=`**、且适配器内**无手动裁切**（§4.3 修-32 / 修-41） |
| 41 | **标准文档是 Pydantic 模型**：非法值在**构造时**即失败，不靠注解 | `page_status="illegal"`、`rotation=45`、`width=0`、倒序 bbox、未知字段 → **全部构造即抛**（§4.2 修-38） |
| 42 | **出现 `uncertain` 页即 `blocked`**（需求 §404，默认不放宽） | 构造一页低质量 OCR → `blocked` + `OCR_UNRECOGNIZABLE`，**不得**进入 `reviewing`（§4.10 修-33） |
| 43 | **`parse_error_code` 已落库且接口可读** | 历史失败记录逐条带稳定码；`GET /api/parses/{parse_id}` 返回 `parse_error_code` 与 `parse_error`（§3.2 修-30） |
| 44 | **`PageStatus` 四态齐备且写入受控** | 断言取值域（含 `uncertain`）；非法状态**构造即失败**（依赖验收 41 的模型校验）（§4.2 修-34 / 修-38） |
| 45 | **`char_map` 能表达多对一，且 bbox 正确** | 含组合字符（`e` + 重音）时存在跨度为 2 的 `SourceSpan`，且该 `DocumentChar.bbox` **== 两个原始字符框的并集** —— **不只查长度**（§4.2 修-39） |
| 46 | **`ParseOptions` 拒绝越界与未知参数** | `dpi=1`、`ocr_min_confidence=5.0`、未知键 → **全部被拒**（§4.5 修-35） |
| 47 | **解析作业幂等键稳定**：并发方按 `parse:{parse_id}:v1` 查到同一条作业 | 并发两次调用 → **同一个 `job_id`**；且键**不含随机后缀**（`version` 留空会退化成一次性键，冲突方将永远查不到）（§3.2 修-42） |
| 48 | **缓存命中不新建作业** | 占位行已 `succeeded` 时再调用 → 作业总数**不变**、返回原 `job_id`、`task_logs` **增加一条**（§3.2 修-42） |
| 49 | **同一幂等键不得绑定不同输入**：命中键时比对 `job_type` / `task_id` / `input_digest` | 同键 + 不同租户 / 不同 `job_type` / 不同 `task_id` → **抛 `IdempotencyConflict`（409）**，且既有作业不被改动；同时断言**正常重复调用仍复用同一作业**（只加"拒绝"而忘了"放过"，会让所有重试都变 409）（§0.8 修-45） |

**T2 的生成方式必须与 `mock_approval` 解耦**（修-18）：

初稿让 `mock_approval` 在运行时用 PyMuPDF 合成合同，理由是"手写 PDF 无法嵌入中文字体"（成立）。
但这会**同时违反两处已确立的约束**：

1. `mock_approval/` 的定位是**外部对接方**，不得依赖 `app/` 的第三方库；
2. §7 风险表承诺"**运行时**的 PyMuPDF 用法集中在 `app/adapters/parse/` 一个模块" ——
   与"mock 也用 PyMuPDF"**不可能同时为真**。

**做法**（两边都不牺牲）：

```text
scripts/make_fixtures.py     ← 开发期脚本，用 PyMuPDF 生成静态中文 PDF
  ↓ 产出（提交进仓库）
mock_approval/fixtures/*.pdf ← 【修-25】放在 mock 自己的目录下
  ↓ 只读
mock_approval/               ← 运行时只读文件，不 import PyMuPDF
```

**为什么这样更好而不只是"更合规"**：

- **夹具变成可版本控制的实物**：静态 PDF 一旦提交，内容就固定了。
  运行时生成意味着"同一份夹具"会随 PyMuPDF 升级而**悄悄改变**，
  而 OCR/字段提取的回归结果也会跟着变 —— 那时很难判断是代码退化还是夹具变了；
- **不变量可断言**：`mock_approval` 里没有 PyMuPDF 这一条可以由测试直接检查；
- `app/adapters/parse/` 仍是**唯一**在运行时使用 PyMuPDF 的地方，§7 的承诺成立。

**夹具不进 `tests/`**（修-25）：第三稿放在 `tests/fixtures/contracts/`，
那会让**运行时的 mock 依赖测试目录** —— 方向反了：

| 问题 | 后果 |
| --- | --- |
| mock 读 `tests/` | 测试套件的目录结构变成**运行依赖**，重命名测试目录会打断服务 |
| 只读 `tests/` 的夹具 | 想在没有测试环境的地方跑 mock（演示、联调）就缺文件 |
| 夹具归属 | 它描述的是**外部审批系统里有哪些附件**，属 mock 的领域数据，不是测试资产 |

放在 `mock_approval/fixtures/` 后，mock 自带样例、可独立启动；
测试只是**额外**去读同一份文件做断言 —— 依赖方向变成 `tests → mock_approval`，
与"mock 是被测系统的外部对接方"这一关系一致。

> 与 §3.4 同一原则：**能被机器核验的约束，不要靠文档声明来维持。**

**关键路径**（按依赖关系逐条推算，**不是各任务工时之和**）：

```text
T1(1.5) → T3(1.25) → T4(1.25) → T7(1.25) → T8(1.25) → T9(1.5) → T10(1) → T11(2) → T12(0.5)
= 11.5 个工作日
```

| 说法 | 数值 | 用途 |
| --- | --- | --- |
| **关键路径长度** | **11.5 天** | 交付周期（这些任务里任何一个晚一天，整体就晚一天） |
| **工时合计** | **14.75 天** | 工作量（单人串行总量，用于排人力，**不是周期**） |

- **`T2` 不在关键路径上**：它只被 `T7` 依赖，而 `T7` 要等 `T4`（第 4 天）才开工，
  `T2` 在第 1 天就完成 —— **余量 3 天**；
- **`T6` 也不在**：`T1 → T5 → T6` 累计 3.75 天，而 `T10` 还要等 `T9`（第 8 天），
  **余量 4.25 天**。

> 第五稿把"工时之和"当成了"关键路径"，两者相差 **3.25 天**。
> 这类错误不影响实现，但会让排期判断失真 ——
> **关键路径的全部作用就是指出"哪些任务晚一天、整体就晚一天"**，
> 写成总量等于这条信息不存在。
>
> 顺带：`T2`（中文夹具）虽然有余量，却决定后面所有验证能否成立（§1.2），
> 因此仍排在前面 —— **优先级与关键路径是两件事，不要把前者当成后者。**

> `T2` 排在前面：它决定后面所有验证能否成立（§1.2）。
> `T6` 的预估累计提到 **1.75 天**（1 → 1.5 → 1.75）：租约、续租、条件完成、
> `lease_token`、回收退避，以及"写结果与完成作业同事务"，都是**并发正确性**问题，
> 比"跑通一次"复杂得多。

## 7. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| **夹具没有合同内容**（§1.2） | 字段提取与扫描件 OCR **无法验收** | **T2 优先**；文本件与扫描件共用同一份中文文本以便交叉验证 |
| **PyMuPDF 许可证 = AGPL-3.0**（§1.3 实测） | 未来闭源交付受限 | 记录为已知约束；**运行时**的 PyMuPDF 用法**只出现在 `app/adapters/parse/` 一个模块**，替换成本可控（不散落到业务层）。开发期脚本 `scripts/make_fixtures.py` 也用 PyMuPDF，但**不进入运行链路**，且 `mock_approval/` 不得 import 它（修-18） |
| **OCR 模型加载失败分类**（复审修正） | 配置错误被当成瞬时错误 → 无意义重试直到耗尽 | **不能一律归为瞬时**：模型目录配置错误 / 文件缺失属**确定性**；仅**推理超时、临时 IO** 可重试。新增 `OCR_MODEL_UNAVAILABLE`（确定性）与 `OCR_INFERENCE_TIMEOUT`（瞬时） |
| OCR 首次运行需下载模型 | 离线环境首次调用失败 | 模型目录可配置；加载失败按上一条分类，**不静默降级** |
| **异常 PDF** | 崩溃或误解 | 五类边界：**加密**（确定性）、**损坏**（确定性）、**超页数**（确定性，配置上限）、**超大渲染像素**（确定性，内存保护）、**渲染超时**（瞬时） |
| OCR 耗时不可控（单页数秒） | Worker 积压 | 单页超时 + 逐页提交 + **续租**；M9 再谈并发与 Redis 队列 |
| Worker 与 API 共用 SQLite | `database is locked` | 领取用单条 UPDATE（短事务）；**OCR 等长耗时在事务外完成**，再入事务写 |
| 解析链路长、失败点多 | 排障困难 | `correlation_id` + `blocked_stage='parse'` + 检查点（M3 已就位） |
| **SQLite 不会自动加列**（§3.5） | 改了 schema 却以为生效，报错出现在查询时 | M4 开发阶段**显式**执行"备份 + `init_db.py --reset`" |
| 把 M9 的事提前做 | 拖期 | §2.2 明确不做；PostgreSQL 的 `SKIP LOCKED` 只**记录待办** |
