# 合同审批审查系统：企业化优化设计（个人双服务器部署版）

日期：2026-09-13  
状态：**已确认，进入实施**

> 本设计已作为《合同审批审查系统-项目计划》v2 的主要依据落地。
> 里程碑按 §16 重排为 M0–M12；M0–M2 成果与编号保留，M3 起进入本设计的工作包序列。
> §7.1 的四个 `write_status` 取值已**严格采纳**：曾短暂扩展的 `rejected` 已删除。
>
> 理由：门禁拒绝与外部失败属于**两个正交维度**。`write_status` 回答"这次回写走到哪一步"，
> 而"为什么没写成功"是另一个问题；门禁拒绝时**根本没有发起回写**，正确状态就是 `not_written`。
> 区分改由独立原因码承担：
>
> ```text
> 门禁不通过：  write_status = not_written    reason_code = WRITEBACK_POLICY_DENIED
> 外部调用失败：write_status = failed         reason_code = APPROVAL_API_ERROR
> ```
>
> 落点为 `comment_logs.reason_code` / `reason_text`（枚举见 `app/enums.py` 的 `WritebackReasonCode`），
> 与 §7.3「错误分类」要求的稳定错误码一致。

## 0. 设计结论

本项目以《大模型项目实战》2.4.1～2.4.12 为强制验收基线，在不删除、不改名、不弱化原始要求的前提下，升级为一个人能够开发、部署和维护的企业形态项目。

目标不是模拟大型企业已有的 Kubernetes、微服务和平台团队，而是实现“企业级边界与质量、个人可承担的运行规模”：

- 后端采用模块化单体，API 与后台 Worker 分进程运行；
- 审批系统、OCR、LLM、对象存储全部通过 Adapter 隔离；
- 原始 7 个工具保留为兼容门面，内部使用幂等后台作业；
- 使用 PostgreSQL、Redis、MinIO 和事务 Outbox 建立可靠闭环；
- React + TypeScript 实现原始 5 个调用端模块；
- 普通业务服务器长期运行，GPU 服务器按需提供 OCR 和 LLM 推理；
- 大模型只做受控提取、语义判断和摘要，不控制流程状态，也不直接回写审批系统；
- 系统只生成审查意见，不代替人工作出审批通过或驳回决定。

## 1. 需求基线与兼容原则

### 1.1 必须完整保留的原始闭环

系统必须完成：

```text
待办拉取
→ 按唯一业务标识去重
→ 审批详情查询
→ 合同附件下载
→ PDF/扫描件解析与 OCR
→ 字段和条款提取
→ 规则审查与证据定位
→ 风险汇总与结果保存
→ 评论回写
→ 异常阻塞与人工重试
```

### 1.2 原始 7 个工具

下列名称和最低参数保持不变：

1. `list_pending_contract_approvals(limit)`
2. `get_contract_approval(instance_id)`
3. `download_contract_attachment(instance_id, attachment_id, file_name)`
4. `parse_contract_document(document_id)`
5. `run_contract_rules(case_id)`
6. `save_review_result(case_id, overall_risk_level, summary_text, focus_points_json, comment_text)`
7. `write_approval_comment(instance_id, review_id)`

允许补充任务查询、人工确认、重试和管理接口，但不能用新增接口替代上述工具。

### 1.3 原始 5 个调用端模块

必须提供待办调用、详情查看、解析结果、规则命中和结果处理五个模块。规则管理与运行管理属于扩展能力，不能挤占五个原始模块的验收范围。

### 1.4 原始数据表

需求规定的 `approval_tasks`、`approval_attachments`、`contract_parses`、`review_rules`、`rule_hits`、`review_results`、`comment_logs`、`task_logs` 全部保留。企业能力通过兼容字段和辅助表扩展，不把原始表替换成另一套模型。

## 2. 当前状态与主要差距

当前代码已完成：

- FastAPI 骨架与健康检查；
- SQLite、9 张表及 ORM 映射（M3 增加 `workflow_jobs` 后为 **10 张**）；
- 40 条种子规则；
- 权威审查上下文、审查批次和四状态评价的数据地基；
- mock 审批系统及评论幂等；
- 规则配置与适用性基础；
- M0～M2 自动化测试。

尚未形成需求闭环：

- 缺少正式 `ApprovalGateway` 客户端和工具 1～3 的业务实现；
- 缺少版本化 PDF/OCR 解析和可靠证据定位；
- 缺少四状态规则评价引擎、风险聚合和 LLM 受控调用；
- 缺少结果保存、人工确认门禁、事务 Outbox 和真实回写编排；
- 缺少 7 个 REST/MCP 工具入口；
- 缺少 React 调用端；
- 缺少 PostgreSQL、Redis、MinIO、Docker Compose 与双服务器部署；
- 缺少完整闭环、故障恢复和线上冒烟测试。

已有《数据模型与规则语义修改方案》继续有效。本设计在其基础上增加企业接入、异步工作流、存储、调用端和部署，不重复定义已确认的四状态与权威上下文语义。

## 3. 方案选择

### 3.1 方案 A：延续同步课程单体

所有步骤在 FastAPI 请求中同步执行，SQLite 和本地文件承担全部存储。优点是代码少；缺点是 OCR/LLM 易超时，无法可靠重试，真实审批系统和并发场景难以接入。

### 3.2 方案 B：早期微服务与 Kubernetes

把接入、解析、规则、模型和回写拆成独立服务并部署到 Kubernetes。扩展能力强，但一个人需要同时承担服务治理、集群、网络、监控和业务开发，当前阶段成本与风险过高。

### 3.3 方案 C：模块化单体 + 独立 Worker + Adapter（采用）

业务代码仍在一个仓库和一个应用边界内，按模块隔离职责；API、Worker、Scheduler 分进程运行。外部依赖使用 Adapter，可靠任务使用队列、数据库事务和 Outbox。

该方案能维持个人开发效率，并保留未来拆分 OCR Worker、模型服务或审批 Adapter 的清晰边界。

## 4. 目标架构

```text
审批系统 / Mock
  ↕ ApprovalGateway Adapter
FastAPI：业务 API + 7 个工具兼容门面
  ↓ 应用服务
审批接入｜附件｜解析｜规则｜结果｜回写｜日志
  ↓
PostgreSQL｜Redis｜MinIO｜Outbox
  ↑
Worker + Scheduler + Outbox Dispatcher
  ↕ OCRGateway / LLMGateway
独立 GPU 服务器：OCR API + LLM 推理 API
```

核心业务模块不得直接导入具体审批厂商、MinIO SDK、OCR SDK 或模型 SDK，只依赖内部定义的端口接口。

## 5. 模块边界

### 5.1 接入模块

负责待办拉取、Webhook 导入、详情同步、唯一键去重和审批字段标准化。它输出内部审批 DTO，不暴露厂商原始字段给解析与规则模块。

### 5.2 附件模块

负责下载、类型与大小校验、SHA-256、恶意文件检查、对象存储和附件元数据。解析模块只接收经过校验的不可变附件版本。

为兼容需求，`download_contract_attachment(...)` 在下载完成后仍返回 `file_path` 和校验信息。这里的 `file_path` 是服务器受控工作目录中的临时物化路径，只供后续解析工具使用；长期保存位置由对象存储键表示。调用端不获得可绕过鉴权的永久公开文件地址。

### 5.3 解析模块

负责原生文本抽取、逐页 OCR、标准文档构建、字段提取、条款识别、质量评估和证据定位。解析结果不能覆盖审批系统或人工确认的权威业务事实。

### 5.4 规则模块

负责适用性、证据质量、确定性条件、受控 LLM 条件、四状态评价和风险聚合。调用端和工具层不得复制规则判断。

### 5.5 结果模块

负责创建审查结果、生成摘要与关注点、计算正文摘要和使过期人工确认失效。外部传入的风险等级必须根据当前审查批次重新校验，不能盲目信任。

### 5.6 回写模块

负责回写门禁、评论生成、Outbox 投递、幂等键、外部写入和回写日志。LLM 和调用端不能直接调用审批 Adapter 写评论。

### 5.7 工作流与日志模块

工作流模块是任务状态转换的唯一入口；日志模块记录业务事件、稳定错误码和审计事件，并对合同正文、凭据和个人信息脱敏。

## 6. 工具接口的同步与异步语义

7 个原始工具作为兼容 facade：

- 每次耗时操作先创建带幂等键的后台作业；
- 短任务在限定等待时间内完成时，直接返回需求规定的业务结果；
- 超时后返回 `task_id`、`status` 和状态查询地址；
- 小文件演示可以走同步完成路径；
- 企业部署默认由 Worker 异步处理；
- 新增查询和重试接口，但不修改原始工具名称与最低参数。

所有 REST、MCP、页面和脚本复用同一应用服务，不维护四套业务逻辑。

## 7. 任务状态、作业状态与可靠恢复

### 7.1 对外业务状态

`approval_tasks.task_status` 保持：

```text
pending / parsing / reviewing / blocked / done
```

`write_status` 保持：

```text
not_written / writing / success / failed
```

状态含义：

- 导入并去重后为 `pending`；
- 下载、PDF 解析和 OCR 阶段为 `parsing`；
- 规则评价、结果处理、人工确认和回写准备阶段为 `reviewing`；
- 评论成功写回后为 `done`；
- 关键步骤无法继续且自动重试耗尽时为 `blocked`。

### 7.2 内部作业状态

新增 `workflow_jobs`，内部状态使用：

```text
queued / running / retry_wait / succeeded / failed
```

业务状态表达合同审查进度，作业状态表达 Worker 执行情况，两者不能混用。

### 7.3 错误分类

- 网络超时、限流、模型服务暂时不可用等瞬时错误：有限次数指数退避，耗尽后 `blocked`；
- 附件缺失、空文件、OCR 完全失败、非法规则配置等确定性错误：直接 `blocked`；
- 单字段证据不足、上下文冲突或单条模型规则无法判断：产生 `needs_review`，不伪装成流程故障。

### 7.4 检查点恢复

任务记录 `blocked_stage`、稳定错误码、可读原因、输入版本和重试次数。人工重试从失败检查点恢复：解析问题回到 `parsing`，规则或结果问题回到 `reviewing`，回写问题只重试回写。

每次人工重试记录操作者、原因和关联失败记录。工作流使用乐观版本或数据库锁，避免多个 Worker 同时推进同一任务。

### 7.5 Outbox

结果保存、回写事件写入和业务状态变更在同一个数据库事务中完成。`outbox_events` 由独立 Dispatcher 发送，成功后标记完成；失败可安全重试。这样数据库提交成功后即使进程崩溃，回写事件也不会丢失。

## 8. 文档解析与证据模型

### 8.1 分层解析管线

固定流程为：

1. 校验文件类型、大小、恶意文件检测结果和 SHA-256；
2. PDF 按页提取原生文本；
3. 仅对无文本或覆盖率不足的页面执行 OCR；
4. 统一生成“页面 → 文本块 → 内容、页码、坐标、字符区间”的标准文档；
5. 确定性解析器先定位金额、日期、主体和条款候选；
6. 复杂语义再交给 LLM，并强制使用 JSON Schema；
7. LLM 证据必须反向匹配标准文档的真实文本块；
8. 执行主体、金额、日期和条款一致性核验。

### 8.2 字段状态

每个字段固定使用：

```text
extracted / not_found / uncertain / failed
```

`not_found` 只表示文档可可靠检索但未发现；解析或 OCR 不可靠时必须是 `uncertain` 或 `failed`，不能被缺失类规则直接解释为合同缺失。

### 8.3 证据结构

每个字段或规则证据至少包含：

```json
{
  "attachment_id": 1,
  "page": 3,
  "block_id": "p3-b12",
  "text": "合同总金额为人民币壹佰万元",
  "bbox": [88, 260, 510, 292]
}
```

需求规定的 `basic_info_json`、`clause_info_json`、`evidence_text` 和 `evidence_position` 保留。完整页面、坐标和中间结果存为版本化 JSON 工件，数据库保存对象键和摘要。

### 8.4 版本和缓存

缓存键由文件 SHA-256、解析器版本和配置版本组成。同一版本不重复 OCR，解析器升级时创建新版本，绝不覆盖历史证据。

## 9. 规则评价、LLM 边界与结果聚合

### 9.1 审查批次

每次审查创建 `review_run`，固定绑定解析版本、权威上下文快照、启用规则及版本、模型版本、提示词版本和配置版本。

### 9.2 四状态评价

每个启用规则在一个批次内产生且只产生一条评价：

- `hit`：规则适用且风险条件成立；
- `not_hit`：规则适用且风险条件不成立；
- `not_applicable`：适用条件明确不满足；
- `needs_review`：上下文、证据或模型能力不足。

固定执行顺序：适用性 → 证据质量 → 确定性条件 → 必要时 LLM → Schema 校验 → 证据反向核验。

### 9.3 LLM 权限

LLM 只允许：

- 在候选文本范围内提取结构化字段；
- 执行需要语义理解的受控规则；
- 根据已保存评价生成中文摘要和关注点。

LLM 不允许改变风险等级、权威上下文、任务状态或人工确认，不允许制造合同中不存在的证据，也不能直接执行评论回写。

### 9.4 聚合与门禁

- 总风险等级取全部 `hit` 的最高风险等级；无命中时为低；
- `needs_review` 不提高风险等级，而使结果完整性成为 `needs_review`；
- 关注点由命中和待判断项生成，并保留规则、原因与证据关联；
- 低、中风险且没有 `needs_review` 时，可按配置自动回写；
- 高风险或存在 `needs_review` 时，必须人工确认当前评论正文；
- 正文变化、重新解析或重新审查会改变内容摘要，使旧确认失效。

系统只写回风险审查意见，不调用审批通过或驳回接口。

## 10. 企业审批接入与租户边界

### 10.1 ApprovalGateway

统一端口提供待办拉取、审批详情、附件下载、评论写入和写入结果查询。Mock 和未来的钉钉、飞书或企业自建审批系统均实现同一接口。

Adapter 独立承担厂商鉴权、分页、限流、签名、字段映射和错误码转换。核心审查模块不读取厂商响应结构。

### 10.2 Webhook 与拉取互补

Webhook 提供及时性，定时拉取补偿漏失事件。两条入口调用同一幂等导入服务，以以下唯一键去重：

```text
provider + tenant_id + instance_id
```

需求规定的 `approval_code` 继续作为业务展示和查询字段。

### 10.3 轻量租户设计

第一版使用默认租户，但从数据、配置、对象键和查询条件中保留 `tenant_id`。目标是避免未来接入第二个企业时全库迁移，不建设计费、套餐和复杂 SaaS 租户平台。

## 11. 调用端设计

调用端采用 React + TypeScript，通过 FastAPI 调用应用服务：

1. 待办调用模块：列表、筛选、业务状态、回写状态和阻塞原因；
2. 详情查看模块：审批表单、附件和权威审查上下文确认；
3. 解析结果模块：字段状态、原文、页码、坐标和 PDF 证据定位；
4. 规则命中模块：重点展示 `hit` 与 `needs_review`，折叠展示另外两态；
5. 结果处理模块：总风险、摘要、关注点、评论正文、人工确认与回写状态。

扩展规则管理和运行管理入口，分别用于规则版本发布，以及日志、作业、重试、回写和审计查看。

前端不能绕过权限、状态和回写门禁；所有决定由后端重新校验。

## 12. 数据与基础设施

### 12.1 PostgreSQL

PostgreSQL 是开发集成和线上环境的目标数据库；SQLite 只保留给快速单元测试及最低成本演示。使用 Alembic 管理数据库版本，同时保留需求规定的初始化脚本和 schema 验证。

### 12.2 Redis

Redis 用于后台任务队列、短期锁和缓存，不作为业务事实来源。任务最终状态、幂等键和审计记录必须持久化到 PostgreSQL。

### 12.3 MinIO

MinIO 保存原始附件、标准文档、OCR 和解析工件。业务表保存对象键、SHA-256、版本和元数据。通过 `ObjectStorage` 端口支持本地文件实现与未来企业对象存储实现。

### 12.4 数据库扩展

在原始表之外增加或完善：

- `workflow_jobs`：后台作业与检查点；
- `outbox_events`：可靠外部事件；
- 审计事件存储：可使用独立表，避免与普通运行日志混用；
- 解析工件和 Provider 调用元数据：只存摘要、版本和对象键，不在日志复制合同正文。

具体字段、索引、外键和迁移步骤在实施计划中逐任务定义，并维持现有 ORM 与 SQL 结构一致性测试。

## 13. 个人双服务器部署

### 13.1 本地开发

开发电脑运行代码、测试和完整 Docker Compose 依赖；Mock 审批系统、Mock LLM 与 Mock OCR 支持不租 GPU 时完成业务开发。

代码通过 Git 推送到远程仓库，再由服务器拉取或由 CI 构建镜像。不得以手工复制散落文件作为正式发布流程。

### 13.2 普通业务服务器

长期运行：

```text
Nginx / HTTPS
React 前端
FastAPI API
Worker
Scheduler
Outbox Dispatcher
PostgreSQL
Redis
MinIO
```

第一阶段用 Docker Compose 管理。各组件是独立容器和独立数据卷，未来可迁移，但当前不引入 Kubernetes。

### 13.3 GPU 服务器

按需运行 OCR 和 LLM 推理 API。业务服务器只通过 `OCRGateway` 与 `LLMGateway` 调用，不依赖具体推理框架。

GPU 服务器停止时，历史结果仍可查看；新作业等待自动重试，达到上限后进入 `blocked`。GPU 恢复后从检查点继续。

GPU API 不直接暴露给普通公网用户。优先使用云厂商内网；无法使用内网时，通过加密隧道或 HTTPS、IP 白名单和独立访问令牌限制访问。

### 13.4 环境

至少区分：

- `local`：个人开发和快速测试；
- `test`：云端完整联调与演示数据；
- `prod-like`：最终部署演示，配置和数据与 test 隔离。

个人项目不建设三套长期在线集群，但配置、密钥、数据库和对象存储命名必须可区分。

## 14. 安全、审计与运维

- 只有 Nginx 的 HTTPS 端口向外开放；数据库、Redis、MinIO 和 GPU 推理端口不直接公开；
- 密钥通过环境变量或密钥文件注入，不提交仓库、不写数据库和日志；
- 合同正文、OCR 全文、模型完整输入和访问令牌不进入普通日志；
- 法务、管理员和只读审计角色实施后端 RBAC；
- 规则修改、上下文确认、结果确认、人工重试和评论回写生成不可变审计事件；
- 附件限制类型和大小，校验摘要，并预留恶意文件检测端口；
- MinIO 使用非公开桶和短期授权；普通调用端不获得永久真实路径，只有附件下载工具按需求返回受控的服务器临时工作路径；
- 数据库和对象存储自动备份，并至少完成一次可验证恢复演练；
- 提供存活检查、就绪检查和依赖健康检查；
- 监控任务积压、处理耗时、OCR/LLM 错误率、阻塞任务和回写失败；
- 为日志建立关联 ID，使一次审批从拉取到回写能够完整追踪。

## 15. 测试与验收

### 15.1 六层测试

1. 单元测试：字段解析、适用性、四状态、风险聚合、状态转换和门禁；
2. 数据库测试：迁移、外键、唯一约束、事务、并发去重与回写幂等；
3. Adapter 合约测试：Mock、审批、OCR、LLM 和对象存储实现遵守统一端口；
4. 黄金合同集测试：文本 PDF、扫描件、缺失条款、复杂金额、方向相反和低质量证据；
5. 端到端测试：覆盖需求规定的完整闭环；
6. 故障测试：GPU 离线、OCR 超时、LLM 非法输出、Worker 中断、重复导入和重复回写。

### 15.2 双重完成标准

需求验收：逐条满足 2.4.12，并能分别演示 7 个工具和 5 个调用模块。

生产质量验收：

- 文本 PDF 与扫描件都能返回可核验的真实证据位置；
- 重复拉取不重复建任务；
- 重复回写不重复产生评论；
- GPU 或 Worker 中断后可以恢复；
- 审查结果可追溯到附件、解析、上下文和规则版本；
- 日志不泄露合同原文和密钥；
- 数据备份能够实际恢复；
- 自动化测试、部署脚本和线上冒烟测试通过。

模型质量不能只用“接口成功”验收。黄金合同集需要统计关键字段准确率、证据定位正确率、规则命中召回情况和不可判断比例，并人工抽查高风险结论。

## 16. 实施分解原则

本设计覆盖多个子系统，不应作为一个无检查点的大任务一次完成。实施计划按以下工作包顺序展开，每个工作包结束时必须有可运行成果和回归测试：

1. M3：ApprovalGateway、工具 1～3、去重与附件保存；
2. M4：标准文档、文本 PDF、逐页 OCR、字段和证据定位；
3. M5：四状态规则评价、确定性规则、受控 LLM 与聚合；
4. M6：结果保存、确认摘要、Outbox、幂等回写与重试；
5. M7：7 个 REST/MCP 工具兼容门面和任务查询；
6. M8：React 五模块调用端及管理入口；
7. M9：PostgreSQL、Alembic、Redis、MinIO 与 Docker Compose；
8. M10：普通服务器部署、HTTPS、备份、监控和发布脚本；
9. M11：独立 GPU 服务器、OCR/LLM 推理 API 与断连恢复；
10. M12：黄金合同集、故障演练、完整闭环和需求验收材料。

现有计划中 M0～M2 的成果保留。实施计划必须先核对实际代码和测试，再调整旧里程碑编号与依赖，不能只修改文档中的勾选状态。

## 17. 非目标

当前版本不实现：

- Kubernetes/OpenShift；
- 微服务拆分和服务网格；
- Kafka 或复杂事件平台；
- PostgreSQL 高可用集群和跨区域容灾；
- 完整 SaaS 租户、计费和套餐体系；
- 同时接入多个真实审批厂商；
- 自建企业级身份中心；
- 24 小时运行的大规模 GPU 集群；
- 自动审批通过、驳回或替代法务作最终决定。

这些能力只有在真实负载、组织和合规要求出现后再引入。

## 18. 设计完成判据

本设计落实后，应得到一个满足以下描述的项目：

> 本地可以用 Mock 和 Docker Compose 完成开发与自动化测试；代码通过 Git 发布到长期运行的普通业务服务器；OCR 与大模型部署到独立、按需启动的 GPU 服务器；系统严格完成需求文档规定的合同审批闭环，并具备版本追溯、证据核验、权限门禁、幂等回写、失败恢复、日志审计和可重复部署能力。
